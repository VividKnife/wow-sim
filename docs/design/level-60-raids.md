# 60级团本设计：25人、核心小队、公会补位

日期：2026-09-20。状态：设计建议＋独立编队原型；未开放正式团本、联机大厅或奖励。

## 结论

首版采用25人团队：玩家保留主角＋4名长期队友，另20个席位由4支公会小队补足。先完成一个人也能完整推进的团本，再增加2—5个真人各带核心小队的自愿合作。真人加入时替换整支公会队，总人数保持25，不因在线人数额外增加战利品或降低首领难度。

不建议把39名完整养成队友作为满级门槛，也不建议把凑齐5名或8名真人作为核心进度前置。40人只保留在本轮设计沙盘里对照，不承诺开发第二套正式难度。

25人比40人少15个作战单位，也更方便在手机上展示5个小队，但实际性能不会必然按人数线性改善：宠物、群体目标选择、光环、投射物和回放仍需测量。缩小人数是为了控制管理量和机制复杂度，不是已经证明的性能优化。

## 与现有系统的吻合点

- `README.md` 定位为手机网页冒险模拟器，已有自动战斗、装备、旅行及小队策略。
- `rules/party.js` 和队伍文档限制4名长期队友，队友已有逐人装备、天赋和生活职业。扩成24／39个同等管理深度的角色，会显著放大整理负担。
- `instances.ts` 已有跨账号加入、角色占用和服务器实例；`model.ts` 当前容量只有5／10／20／40，**25尚未被正式服务支持**。正式开发应让内容定义决定容量，移除由请求随意选择实例规模的设计，而不是只给枚举加25。
- `combat-execution.ts` 已按参与账号决定单人预计算或多人实时。一个账号带25个单位依然是单人，不应因为人多切成联机模式。
- 已有实例不等于已有可玩的联机组队产品：大厅、邀请权限、准备检查、队长交接、断线托管、共同进度和各账号掉落仍需实现。
- 当前可玩地下城以死亡矿井、监狱为主，职业到60级不等于完整1—60内容已经存在。先用独立60级测试夹具验证首领，不把团本上线与所有中期世界内容混在一次改动中。

## 为什么不选另两种方案

| 方案 | 收益 | 主要问题 | 判断 |
| --- | --- | --- | --- |
| 单人逐个培养39名队友 | 自由配队、单人可玩 | 装备与技能管理量陡增；手机界面负担大 | 不作默认模式 |
| 8名真人各带5人，共40人 | 社交协作和共同开荒感强 | 同时在线、职责协调、断线与奖励成本；低人口时核心内容不可达 | 不作为首版 |
| 5名真人各带5人，共25人，必须凑齐 | 人数减少，核心队资产可复用 | 仍有缺一人无法开团和五坦冗余问题 | 不强制凑满 |
| 25人，1—5名真人＋公会补位 | 单人完整、朋友随时加入，管理量可控 | 需要稳定的公会AI与职责规划；单人社交感较弱 | 推荐，先单人后合作 |

## 坦克与治疗：归属按小队，作战按全团

常规首领以2坦、5治疗、18输出为设计起点，并非原版考据结论或强制入场条件。不同遭遇可用3坦、4治疗、18输出，或2坦、6治疗、17输出；相应调整机制和输出窗口。

| 归属小队 | 坦克 | 治疗 | 输出 |
| --- | ---: | ---: | ---: |
| 玩家A | 1 | 1 | 3 |
| 玩家B | 1 | 1 | 3 |
| 玩家C | 0 | 1 | 4 |
| 玩家D | 0 | 1 | 4 |
| 玩家E | 0 | 1 | 4 |
| 合计 | 2 | 5 | 18 |

这只是易理解的组合示例。也允许某队带2治疗、另一队无治疗；治疗可治疗全团，坦克可承接任何已分配目标。不要创建五个互不支援的5人副本。

角色保存两套配置：地下城配置和团本配置，各包含职责、合法天赋方案、技能策略、装备引用。营地／首领间可切换，战斗内禁止瞬间换整套天赋装备。首版建议已保存配置切换不额外收金币，团本失误不应导致重复付费洗点；新天赋的获取仍沿用成长规则。

“战士坦切输出”需要输出天赋、武器与策略，“德鲁伊切副坦”需要有效坦克配置。法师不能换成坦克，勾选职责不直接获得坦度或奶量。保存配置引用已有物品，不克隆装备，切换时校验所属角色、穿戴条件、锁定和装备冲突。提供基础副职责配装获取路径及缺装提示。

不要强制三个玩家的主角坦克改输出。可以让其同行的AI坦切输出，或者交换团本出征人选。后续可增加少量**替补席**而不增加同时出战人数；不是首版就强迫每人养十个角色。当实际角色无法满足分工时明确显示缺口，允许保留部分公会补位或重新准备，不把任意职业伪装成万能角色。

组队大厅显示全团职责与功能缺口，按角色实际配置计算；有空位时推荐适合的公会编队。不能按真人数量给首领自动削伤来掩盖错误阵容。建议阵容检查是提示，不是通关判定，也不因某个治疗少一人就拒绝开战。

UI首屏展示5张小队卡、全团坦疗输出概览、驱散／打断缺口和首领战术；细看时再展开单人。正式战术分配到角色和目标，小队任务是批量编辑与默认优先级，并不把整队所有人锁成同一职责。

## 核心队与公会队如何成长

核心5人保留逐人配装、天赋、技能与生活职业，是主要长期投入。公会20人仍有名字、职业和真实战斗实体，但以4支小队管理：选择编制、职责和战术模板，服务器将模板展开为合法技能、装备和策略。不要增加20套背包、银行、生产订单与日常补给界面。

首次解锁提供可打入门首领的基础公会队，强度不超过玩家可取得的入门装备。当前公会队采用固定基础配装，不设公会补给或训练。核心五人通过掉落装备提升实际能力；另设金团模式，以招募、竞拍和分金作为经营体验，见[金团设计](gold-raids.md)。

不设计“NPC随机犯错”作为主要难度。正确分工应稳定执行；失败来自能力不足、覆盖冲突、法力、站位或时序。战报需要指出具体原因，例如护卫未被接住、驱散排队、治疗耗尽，而不是只有伤害排名。

单人首通重点是观察机制、调整配装和AI规则，再次挑战。常规移动、治疗和驱散交给既定策略；不要让手机玩家临场点25个角色。首版不强制几秒内反应的QTE；确需手动的挑战模式另行标明。

## 40人首领怎样改成25人

不能把所有数值统一乘0.625。以下是调参方法，不是现有首领平衡已完成：

| 项目 | 建议方法 |
| --- | --- |
| 首领生命 | 目标阵容的有效团队DPS × 目标击杀时间。有效DPS包含移动、驱散、转火损失与坦克贡献；0.625仅可作为首轮粗估 |
| 对主坦普攻／重击 | 按60级坦克有效生命、减伤与分配治疗确定危险窗口；人数下降并不意味着坦克血量下降37.5% |
| 全团伤害 | 按人均伤害、覆盖人数、频率和5名治疗的有效恢复能力校准；不同时对人数与伤害二次缩放 |
| 点名／诅咒 | 调整人数和间隔，验证实际可用驱散职业、冷却与法力；“会驱散”不能替代正确的驱散类型 |
| 增援 | 优先减少同时目标数、波次或控制需求。坦克需求由并发目标决定，不由总人数线性决定 |
| 场地与群体技能 | 重新检查分散空间、站位半径、小队增益范围及群疗目标上限 |
| 狂暴时间 | 给正确策略、合理装备留下容错；不能靠过多坦奶无限拖过 |
| 掉落 | 按账号／核心队的成长速度单独设计，不按25个角色各发完整奖励，也不照搬40人的共享掉落量 |

固定25个作战单位，真人从1变5时不再缩放首领。人与AI使用同一技能、仇恨和数值规则；协作的优势来自交流与策略，而非真人专属伤害加成。

## 首领节奏、进度与奖励

建议首领单次战斗目标3—5分钟，一次游玩可以完成一个首领的准备、数次尝试与复盘；这些是待验证目标，不是已经测出的时长。首通后才允许已验证路线自动推进，避免未知首领离线自动通关。

首版选熔火之心主题的一个双目标／驱散首领做完整纵向闭环，再增加不同考点的2个首领。正式使用原版名字前逐个建立来源记录和“本作25人改编”说明。当前沙盘的守门战、兽群战、熔岩战都是自定义机制练习，不冒充原版首领技能。

保存首领检查点，团灭保留此前进度，允许准备后重试。正式单人战斗沿用服务器权威时间与检查点；不新增客户端暂停后回到过去发指令的机制。

建议采用账号／核心队维度的每周首领奖励资格，战斗尝试不限，首杀获得确定的兑换进度并有个人掉落。单人和合作共享奖励资格及装备上限；公会NPC不参与个人装备分配，只获得队伍成长资源。多人每个合格账号各自结算，不共享掷骰，不因NPC占比增减核心队收入。

实际掉率、每周数量与保底门槛要基于五人共同养成速度测试后确定。身份与奖励键至少包括账号、内容、首领、周期；未参战／战斗中才加入者不获本次奖励，重复请求与worker重试不能重复发放。断线成员继续执行已提交策略则保留资格。

## 联机放在什么阶段

先完成单人核心循环，第一版合作支持2—5个真人，空位公会补齐。只在营地或首领间更换队伍；加入后重新检查职责，不能直接挤掉正在承担主坦的NPC。

开战前冻结本场角色配置并让所有真人确认；等待时可退回公会队继续推进。成员短时掉线由原策略接管，本场不中断，不把掉线视为无限期阻塞整个实例的理由。首领间离队释放其角色占用，用公会队补位并重新准备；团长离开需交接管理权。当前服务里队长退出和离线期限的限制需要同步重构。

团长决定路线、标记和公共战术，账号仅修改自己的角色与装备。别人的治疗技能以我方角色为目标是合法支援，不等同于控制或修改对方角色；必须按动作区分权限，不能一概禁止跨账号目标。

应先证明朋友合作的价值：分担副坦、驱散与支援策略、共同复盘和分享构筑。无需把更高装备上限藏在必须联机的模式里。未来如有稳定团队和竞争需求，再加挑战成绩、外观与排行榜。

## 实施边界与验收

1. **本轮已做：编队沙盘。** 独立页面、25／40人数对照、真人席位示例、公会模板切换、战术覆盖诊断、五人合作2坦5疗18输出示例。纯函数可序列化，不读取账号和存档。检查通过只表示覆盖人数与任务，不表示击杀。
2. **已新增：独立单人双首领Demo。** [熔火之心试玩](../development/molten-core-demo.md)使用25名预设真实角色，复用职业规则，完成鲁西弗隆、玛格曼达、跨队治疗、战报、本机检查点、团灭重试与Demo奖励。现已进一步接入[正式游戏](../development/guild-raid.md)：拥有独立资产的五人核心队、仅存在于实例的20名公会单位、25人容量和权限校验、周奖励、营地恢复及持久化进度。
3. **之后：扩展公会成长与更多首领。** 验证至少两种不同阵容能够通过同一首领；错误策略应有可解释的失败，不以单一战力阈值代替机制。
4. **最后：可选合作。** 邀请权限、准备检查、跨账号合法支援、快照同步、断线接管、团长交接、锁定资格与奖励事务。先少量朋友实测再扩并发。

玩法验证重点：从进入营地到第一次开战是否足够快；玩家能否从战报说出一个可改进点；再次尝试时是否愿意调整而不是只挂机刷装备；增加朋友是否增加协作乐趣而非纯等待。正式性能验证需包含25人＋宠物、群体技能、连续首领、服务器重启、回放分段和手机帧率，不能把当前5人测试结果当25人容量保证。

## 运行本轮原型

```powershell
node apps/web/scripts/serve-raid-planning-preview.mjs
# http://127.0.0.1:5188/raid-planning.html
node --test packages/game-domain/test/raid-planning.test.ts
```

文件：`packages/game-domain/src/raid-planning.ts`、`apps/web/test/browser/raid-planning.tsx`。模块仅用于设计预演，不是服务端请求校验或首领战斗实现；驱散能力是示例布尔值，不含职业、法术类型、冷却或目标验证。原型配置切换可替换整队职责，正式角色只能切换实际支持的配置。

原型无持久化，刷新回到默认示例；未接主游戏菜单、没有真实匹配或房间，也没有按25人改完现有战斗数值。

本轮验证：11项规划规则测试、根目录TypeScript检查、Web TypeScript检查通过。浏览器检查了默认单人、五人合作2坦5疗18输出、撤销驱散分工后的诊断和40人切换；390px手机及1280px桌面布局完成检查，浏览器未捕获错误或警告。未执行正式首领战、生产服务联机或并发压测。
