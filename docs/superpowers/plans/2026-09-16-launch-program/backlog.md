# 开发拆分、依赖与交付安排

> For agentic workers: 执行时使用 `superpowers:executing-plans`，或在明确启用子代理后使用 `superpowers:subagent-driven-development`。按复核门槛逐项执行。

**Goal:** 在保留现有游戏的基础上，交付双阵营 1—60 全世界、真人联机与首批团本的可上线版本，并分期完成经典旧世后续内容。

**Architecture:** 确定性规则核心 + 版本化内容包 + 服务端权威个人/实例状态 + 只读表现视图。模块化单体起步，实例运行器通过契约隔离。

**Tech Stack:** 当前 ESM/Node 测试、React/TypeScript、Sites/Cloudflare、D1；有状态实例部署由 NET-01 验证后决定。

**Spec:** [总规划](README.md)、[内容清单](content-matrix.md)、[审计基线](audit.md)。

**最新架构前置：** 按[最终产品架构评估](../../specs/2026-09-16-target-architecture-review.md)的 A0—A5 优先建立多角色、活动、资产、实例与新客户端协议。下方工作包可复用，但须按该前置拆子任务；不能先把外派/个人专业叠加到将被替换的单状态引擎。

## 全局约束

- 首发 G1 包含两大陆全地图、1—60 双阵营、九职业、真人组队、熔火之心与奥妮克希亚；其余团本按阶段。
- 普通坐骑 20 级；迅捷坐骑 60 级；既有便捷玩法单独标注为改编。
- 最新队友范围：副本佣兵与长期伙伴；每角色任务装备；主角/伙伴各自双主要专业；专业收益归执行者；实时外派采集和共用制造页面。详见队友设计的用户要求/建议边界。
- 规则版本、数据版本、内容阶段、改编配置分别管理；不得提前投放阶段外奖励。
- 所有随机数与游戏时间来自权威状态；浏览器不能提交金币、经验、物品或掉落结果。
- 本轮任务不依赖活动工作区的临时文件；必须从包含现有成果的冻结提交启动。
- 按当前 AGENTS.md，不兼容旧存档/旧接口，不建设兼容层、字段别名、双版本读写或旧档迁移；同步更新消费者和当前需求测试。
- 新玩法到达 Verified 必须有实际执行路径、正常获取方式、失败/恢复和集成证据。
- 路径是目标归属；新增目录在相应任务开始时创建。未完成前不要声称文件/命令已经存在。

## 2. 工作分解总表

下面是父工作包，不允许把 L 包直接发送为“持续开发直到完成”。S 约一个可独立复核交付，M 拆 2—4 个，L 拆 5—12 个；含整片区域/大型副本时继续按任务链、首领或机制拆分。每个子任务建议 0.5—2 个预算工作日、一个明确验收结果；预算须用实际吞吐校准。

角色：I=集成/架构；C=核心规则；D=数据/世界；N=联机/服务端；U=客户端；E=经济；Q=质量/运维。角色是职责，可在有限执行槽中轮换。

## 6. 工作项状态与完成定义

`Proposed → SpecReady → Ready → InProgress → Review → Integrated → Verified → Released`，另有 `Blocked`。

Ready 必需：范围、依赖及版本、唯一负责人、允许文件、输入/输出契约、失败场景和验收命令。Review 必需：diff、测试证据、行为说明、已知限制、运行成本变化。Verified 必需：已合入候选分支并通过相邻模块及端到端检查。

拒绝以下“完成”口径：只有测试夹具能玩、只在手工加等级/赠装备后通过、改掉数据使怪物不再危险、忽略失败测试、依赖其他工作区未提交文件、把 UI 菜单存在算成功能完整。

## 7. 工期与预算滚动更新

每张子卡记录：设计耗时、编码耗时、等待依赖、首次复核结果、修复轮数、合并耗时、验证耗时、模型/工具用量（可获得时）与产物规模。

每 10 个 Verified 子任务更新同类型中位数和 P80，不用源码行数作为效率。若合并等待超过执行时间，减少同时写代码的人数；若数据校验稳定且队列短，增加独立内容包作者。

总规划的 20—32 周仅为早期资源情景；任务量、验收吞吐和关键路径确定后再给目标日期。未实测的平台费用不填精确货币值；成本模型至少含活跃模拟 CPU、连接、数据库读写、对象存储、资源流量、日志和备份。
