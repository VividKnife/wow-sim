# Codex 并发开发与集成手册

本文件是今后执行方案，不代表本次已经建立工作区、启动任务、创建 PR 或改变其他任务状态。项目范围以 [总规划](README.md) 为准，工作项以 [backlog](backlog.md) 为准。

当前仓库 AGENTS.md 已明确允许破坏性重构且不要求历史兼容。以[最新架构评估](../../specs/2026-09-16-target-architecture-review.md)组织第一轮工作；旧存档/旧接口可直接替换，同步更新所有消费者和测试，不建设旧格式兼容层或迁移。

## 1. 现在先做什么

当前多个活跃任务共用 `C:/workspace/wow-sim`，而 Git HEAD 还没有包含多数新功能。不要直接从旧 HEAD 开十个任务，也不要直接移动一个仍在写入的任务并期待未提交改动自动分清归属。

1. 让正在做职业、专业和主线验证的任务收口，整理各自改动与完成证据。暂停追加新的共享文件开发需求。
2. 集成任务读取整个 diff 和这些报告；按当前源码重新测试，解决或明确归属失败。
3. 形成包含现有游戏成果的可重建提交，记录该 SHA 和数据摘要；只有全量门槛通过才作为 G0。
4. 新任务从 G0 对应分支启动独立 Worktree，使用 `codex/<领域>-<任务编号>` 命名分支。
5. 每个工作区独立安装依赖、独立构建目录、独立本地存档/端口。共享只读数据缓存可以，但不得共享可写数据库。

Git worktree 的隔离能力和 Codex 中的入口见[官方文档](https://learn.chatgpt.com/docs/environments/git-worktrees)。这里的分支策略、队列和阈值是项目管理建议。

## 2. 组织方式

### 一个持续存在的集成任务

管理版本、任务状态、文件归属、接口、候选分支、失败归属和发布证据。只接收有明确交付物的任务，不把上下文不断膨胀的大对话当作唯一项目记忆。

集成任务负责公共文件和公共接口变更。它可以实施小适配，但不要同时承担一个大型职业或副本，否则整个项目会等待合并。

### 多个短生命周期执行任务

每个任务对应一个可独立验收结果，例如“银松森林某任务链”“某首领的召唤机制”“共享掉落重试不重复发奖”。同一个任务不要把数据导入、联机重构、UI 美化和版本升级混在一起。

以 3 个执行槽起步：一个处理关键路径，一个生产独立内容，一个验证或做另外的独立模块。复核由其中空出的槽轮换，避免所有槽都写代码却无人验收。

### 独立复核

先核对规格与 scope，再检查实现与失败模式。审查者不能仅凭作者的摘要给出通过。简单数据修正可以用短复核；影响存档、经济、并发、公共契约和团本锁定的变更必须专门审查。

## 3. 文件归属和共享热点

| 文件/模块 | 唯一负责写入的角色 | 其他任务如何协作 |
|---|---|---|
| `engine.js`、`catalog.js` 公共入口 | 集成/核心 | 提交新模块和必要接口提案，由集成接线 |
| `character.js` 公共属性与实例结构 | 核心 | 职业作者修改独立机制模块，结构变更走契约版本 |
| `apps/web/app/game.tsx`、全局样式 | 客户端集成 | 页面作者提供独立组件和局部样式 |
| `app/api/game/route.ts`、认证、schema | 后端/持久化 | 不允许区域/职业作者顺手加列或绕过鉴权 |
| 数据库 migrations、journal | 单一后端作者 | 串行分配迁移编号；禁止手工同时改 journal |
| package/lockfile、CI、部署绑定 | 集成/平台 | 各任务提出依赖需求；不各自升级框架 |
| 世界/副本/团本数据 | 分包作者 | 每包唯一目录，跨包引用稳定 ID，统一生成索引 |
| 公共战斗效果处理器 | 核心 | 首领/职业作者先登记所需机制，不能复制一个私有伤害引擎 |
| 资产 manifest 与生成文件 | 数据管线作者 | 修改来源/覆写文件后生成，不直接手改大型 JSON |

worktree 之间不会互相覆盖，但同时改同一公共文件仍会合并冲突。允许不同分支提交冲突提案，不允许通过“接受我的整份文件”覆盖已经整合的他人功能。

## 4. 并发前冻结的接口

下列为建议的 v1 草案，CORE-01 负责核实后冻结；不是当前代码已有接口。

```ts
type Scope =
  | { kind: 'character'; id: string }
  | { kind: 'party'; id: string }
  | { kind: 'instance'; id: string };

type CommandEnvelope = {
  protocolVersion: 1;
  requestId: string;
  scope: Scope;
  characterId: string;
  expectedRevision: number;
  clientSequence: number;
  type: string;
  payload: Record<string, unknown>;
};

type EventEnvelope = {
  protocolVersion: 1;
  scope: Scope;
  sequence: number;
  revision: number;
  simulationTimeMs: number;
  type: string;
  payload: Record<string, unknown>;
};

type SnapshotEnvelope = {
  protocolVersion: 1;
  scope: Scope;
  revision: number;
  lastSequence: number;
  simulationTimeMs: number;
  rulesetVersion: string;
  dataVersion: string;
  contentPhase: string;
  view: Record<string, unknown>;
};
```

`characterId` 必须与已认证会话及控制权匹配，不能因为用户提交了该字段就信任它。事件 payload 按接收者权限过滤；Snapshot 是客户端视图，不含权威 RNG、未来战利品或其他用户私有背包。

冻结时将 `type/payload` 收紧为判别联合和运行时校验，逐个定义命令；本草案中的 `Record` 仅表达边界，不应作为生产接口最终类型。

核心约束：

- RNG 状态和模拟时间仅存在权威存档；事件同时间的排序规则固定。
- 同一个 requestId 与不同 payload 冲突时拒绝；重复相同命令返回已有结果或当前一致视图。
- 序列不连续时客户端请求快照；服务端验证 revision，不接受客户端“修复后的状态”。
- 角色进入实例：个人活动结清 → 记录移交意图 → 获得实例租约 → 状态提交。每个步骤可恢复，避免两个所有者同时产出收益。
- 发奖：实例持久记录唯一 `settlementId` → 角色服务幂等入账 → 确认；在任一步崩溃都可重试。一个人的失败不能让全团重复发奖。
- 物品使用全局唯一实例 ID，来源和所有权可查；不要沿用不同角色都可能生成的本地 `i1` 作为全局主键。
- 交易：先托管资产并在同一经济权威边界执行；不把跨工作进程依次改两个 JSON 当成事务。
- 内容包只能调用规则层能力，不能写账号、数据库或网页。机制模块不能反向依赖 React。

## 5. 任务输入模板

方括号内容由集成任务在派发前填写；这是模板字段，不是允许执行者自行猜测的需求。

```text
任务：[ID + 一个明确交付物]
工作区：[独立 worktree 路径]
基线：[提交 SHA]；分支：codex/[领域]-[任务编号]

先读取：
- docs/superpowers/plans/2026-09-16-launch-program/README.md
- 对应内容清单、任务卡、已冻结接口和项目 AGENTS.md（若存在）

目标：[可观察的结果]
已完成的前置：[依赖任务 + 接口版本]
允许修改：[精确目录/文件]
需要但无写权限的公共变更：提交接线说明，由集成任务处理。

输入：[内容包/命令/夹具/来源]
输出：[接口/事件/文件/报告]
必须保持：[原有行为、版本和改编规则]
失败场景：[重试/越权/阶段未开/缺材料/断线等具体场景]
验收：[精确命令 + 预期行为 + 必要手动操作]

一个任务完成一次独立验收，不扩大范围。
引用数据必须标明来源与版本；不能伪造原版数值或宣称未测的功能完成。
发现依赖未就绪，提交缺口和可独立完成部分，不修改他人契约绕过。
结束提交：改动摘要、SHA/diff、测试证据、未验证项、集成步骤和风险。
不修改其他工作区，不合入集成分支，不发布，不清除用户存档。
```

### 可以先复制给集成任务的启动指令

```text
执行 docs/superpowers/plans/2026-09-16-launch-program/backlog.md 的 GOV-01，
先完成当前 wow-sim 开发成果收口和可重建基线。阅读 audit.md，但以当前源码复核。
先查相关 Codex 任务状态及 Git diff，不中断正在运行的其他任务，不重置其修改。
核对九职业60级、全配方、主线1—20的完成证据，复现全量检查的失败并拆修复卡。
在安全收口后创建包含现有成果的基线提交，记录测试、类型、构建与数据摘要。
随后完成 GOV-02/GOV-03 的协作规则和版本/保档政策文件。
这轮交付是稳定开发起点，不提前开发新地图或上线。
```

### 内容任务示例

```text
在已经分配的独立 worktree 中，实现 WORLD-02 下的一个“提瑞斯法初始任务链”子任务。
执行前读取冻结的区域 schema、任务机制接口、版本和原始来源。
仅修改该任务链的数据包、专用测试与验证报告；不修改 engine/catalog/schema。
交付完整接取前置、目标NPC/怪物/对象、奖励和相邻链衔接。
测试亡灵合法角色从出生地正常完成；错误阵营、任务已完成、满包、
重复领奖、离线推进和前置缺失均有明确结果。
若发现任务类型没有处理器，提交公共机制工单，不在数据中伪造奖励跳过。
```

### 独立审查指令

```text
只读审查 [任务ID] 在 [baseSHA..headSHA] 的改动。
先核对其规格/允许范围，再检查正确性，重点关注与相邻模块的接口。
重跑声明的验证，区分夹具测试与真实持久化证据。
检查版本、数据来源、阶段过滤、重试/越权/恢复和资金物品守恒。
输出可操作的问题：严重级别、精确位置、复现方式、影响和建议。
没有问题时说明覆盖范围及未验证部分，不仅复述作者“测试通过”。
```

### 集成指令

```text
将已获复核通过的 [任务ID/提交] 合入候选集成分支。
先确认基线/接口版本和现有分支差异，保留其他已合入功能。
解决公共入口接线和迁移顺序；语义冲突回到相应作者修正。
运行改动模块、相邻消费者及项目必需检查，生成冻结证据报告。
只有整合结果通过才把任务从 Review 改为 Integrated/Verified。
此操作不包含生产发布或清档。
```

## 6. 合并列车

1. 作者在自己的分支完成实现、测试、报告和提交。
2. 复核者阅读规格和 diff，复现重要正反例；有阻塞问题则退回作者。
3. 集成任务按依赖顺序一次合入一个任务，先契约与 schema，再实现与内容，再界面。
4. 冲突时比较行为和测试，不机械接受整份文件；补回缺失的相邻用例。
5. 跑必需检查；涉及公共规则时跑全量回归；内容包运行引用/阶段/正常回放，不能只做 JSON 格式检查。
6. 每个集成批次输出可玩预览和证据，达到里程碑时冻结候选版本。

整合失败不能以“其他并行任务造成”作为合并豁免。允许说明归属，但候选版本仍保持失败状态，直到修复或按照明确范围撤回该变更。提交、推送和发布必须对应具体交付授权，不能被模板自动触发。

## 7. 验证层次

| 层次 | 必测内容 | 主要用途 |
|---|---|---|
| 数据 | 来源、ID、闭包、阶段、获取路径、地图连通 | 防止只导目录或跨版本混用 |
| 机制 | 公式边界、时间排序、光环覆盖、威胁、资源 | 确定性与战斗正确性 |
| 场景 | 职业等级节点、任务链、首领成功/失败 | 验证玩法真实生效 |
| 持久化 | 并发保存、事务、幂等、租约、故障恢复 | 防重复收益和丢档 |
| 网络 | 多用户、乱序、重复、弱网、重连、旧版本 | 验证真人联机 |
| 浏览器 | 正式 API、手机布局、前后台与输入 | 验证用户能实际操作 |
| 长旅程 | 正常命令 1—60、完整副本/团本 | 验证内容衔接和成长经济 |
| 发布 | 容量、观测、备份恢复、灰度、回滚 | 验证可运营 |

模拟测试允许加速外部时间，但必须走正常游戏命令、不注入奖励；性能/战斗机制夹具可以直接设置角色状态，但报告中不得冒充完整正常成长。

数值测试使用固定来源的黄金案例和有统计解释的随机检验。UI 截图、类型检查和大量测试通过都不能独立证明原版数值准确。

## 8. 容量与派工规则

- 起步 WIP：3 个执行 + 1 个集成；审查占用执行槽，避免无限生成待审任务。
- 同一个核心文件同时最多一个作者；同一个 schema 版本只有一个迁移负责人。
- 队列达到 3 个待复核/待合并任务时暂停新派工；先清队列再扩容。
- 只有在连续两批集成无公共契约返工、任务等待小于执行耗时、算力与额度足够时扩到 6—8 个执行任务。
- 先扩不同区域和只读审查；不要同时开 9 个职业代理共同修改一个战斗文件。
- 缺依赖超过一个工作日，拆出上游最小交付或换独立任务，不让代理不断猜接口。
- 公共接口变更需列消费者、新夹具、同步替换与旧实现删除顺序；破坏性变更集中到一个集成批次，不保留历史兼容层。

## 9. 项目事实保存

建议后续落地以下持久记录，由 GOV-02 统一创建，而不是每个任务单独发明格式：

- `docs/project/decisions.md`：已确认产品与技术决定，保留日期和取代关系。
- `docs/project/ownership.md`：模块/文件归属与当前作者。
- `docs/project/tasks.json`：任务 ID、父任务、状态、依赖、baseline、分支、SHA、证据路径、阻塞原因。
- `docs/validation/<milestone>/`：冻结测试、数据、性能、回放、截图和缺陷报告。
- `docs/releases/<version>.md`：开放内容、规则变化、迁移、回滚和已知问题。

本次没有新增全局 AGENTS.md，避免在其他任务仍运行时突然改变其约束。GOV-02 收口后再把稳定协作规范写入仓库指令。

## 10. 每日/里程碑管理

每日只需要回答：哪些任务达到 Verified、关键路径下一项是什么、哪些接口/缺陷阻塞、合并队列是否过载。不要把正在编码的数量作为进度。

每个里程碑必须提供：可玩版本、首发清单覆盖、失败/缺口清单、性能/成本变化、用户体验观察及下一批 Ready 任务。范围改变必须更新总规划与受影响任务，不能只留在某个历史对话里。

发布前集成任务最后核对：首发范围是否完成、当前 SHA 是否已验证、数据库/数据是否兼容、备份是否恢复过、目标用户是否能登录、资产发布依据是否齐备、回滚路径是否实际可用。只有具体候选版本通过，才进入正式发布决定。
