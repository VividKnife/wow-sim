# 手机本地模拟：数据加载调查与改造方案

日期：2026-09-29。调查基线：`8c50cb11afc4ad17f22eaa91415b85a02d41a22b`。
本报告是代码、构建产物与桌面隔离实验的研究结果；没有实施运行时改造，也没有发布新版本。不能据此确认 iPhone 自动刷新就是内存终止。

## 结论

可以按当前活动加载数据。推荐结构是 **小型通用规则引擎 + 按区域/副本/参战职业组织的数据包 + 独立展示资料**。首先拆数据和初始化工作，暂不优先拆各职业的计算代码。

当前所谓“80 MB 规则”主要是整套静态数据库，包含副本手册的掉落追溯信息。职业资料只占共享包约 16%，且其中也有大量说明、来源和重复数据。只按职业裁剪，无法解决全世界数据同时加载的问题。

## 80 MB 的实际构成

重新执行 Next.js 生产 webpack 构建，捕获 stats，并读取生成 chunk 内各 module 函数的 UTF-8 字节数。下表采用十进制 MB，计入 JSON 字符串转义；不是源码目录大小或内存占用。剩余项含模块包装开销。

| 内容 | 实际字节 | MB | 含义 |
|---|---:|---:|---|
| world-reference.json | 37,772,341 | 37.77 | 世界怪物、刷新点、任务、物品、法术、掉落表、26 个副本定义等 |
| dungeon-journal.json | 12,970,955 | 12.97 | 28 个副本的首领手册、重复掉落条目和来源路径 |
| classes-reference.json | 12,899,552 | 12.90 | 九职业技能、天赋、创建角色数据、物品、获取条件、资料来源等 |
| classic-reference.json | 8,475,852 | 8.48 | 基础数据库，包含与其他资料包重叠的条目 |
| stockades-reference.json | 3,397,849 | 3.40 | 监狱副本原始表及路线资料 |
| professions-templates.json | 1,666,057 | 1.67 | 专业相关物品和法术模板 |
| 其他模块及包装 | 3,082,774 | 3.08 | 死亡矿井、脚本、专业配方、查询表等 |
| **共享 chunk 合计** | **80,265,380** | **80.27** | `9531.cd0efcdca6d24fd2.js`，本次本地构建 |

模拟 Worker 入口另有 9,420,744 B，策略 Worker 入口另有 8,755,841 B；手机现在不启用第二个策略 Worker。共享 chunk 离线 gzip 为 10,187,964 B，不能据此声称线上传输启用了相同压缩。压缩只能减小传输，不能消除解码后的对象和索引。

为得到整个模拟 Worker 的来源归因，另用 esbuild 将其打为单包：94,828,962 B，其中 JSON 贡献 94,072,782 B，非 JSON 代码贡献 756,155 B。**此口径是完整依赖图，不是上表的共享 chunk**；不同打包器的编码、压缩与拆块不同，不能直接相减当作优化收益。

完整依赖图还包括约 5.72 MB 的怪物模型与 NPC 模型索引（esbuild 输出口径），以及本地化、图标和物品展示数据。这里是索引元数据，不是下载了全部 3D 模型文件。

## 最大数据包内部还有什么

`world-reference.json` 的主要表（紧凑 JSON 字节数，未计 JS 字符串转义）：

| 表 | 行数 | MB |
|---|---:|---:|
| 怪物掉落 | 152,076 | 8.68 |
| 怪物刷新点 | 65,078 | 4.10 |
| 任务 | 3,837 | 4.06 |
| 场景物件刷新点 | 47,695 | 3.82 |
| 物品模板 | 11,529 | 3.58 |
| 怪物模板 | 7,297 | 1.98 |
| 法术模板 | 5,027 | 1.86 |
| 引用掉落表 | 32,460 | 1.40 |

副本手册包含 24,657 个首领掉落条目，物品会在不同首领下重复出现。仅在内存中的实验副本去掉 `loot[].source`，紧凑 JSON 就从 **12,965,891 B 降到 4,947,590 B**，减少约 62%。这不是可直接发布的删字段补丁：`dungeon-journal.js` 目前读取来源路径来判定共享掉落，应先在编译时生成 `shared` 和来源类别，再移除运行时追溯原文。还可将物品详情按 ID 去重、将每个副本手册独立加载。

职业资料也不是 12.9 MB 的职业算法：`tables` 约 4.53 MB、`classContentManifest` 约 2.70 MB、`classQuestSources` 约 2.64 MB、九职业能力列表约 0.78 MB，此外还有初始装备、翻译、天赋等。部分 provenance 被运行逻辑用于技能获取和宠物训练，不能统一删除所有 `sources`；应编译成明确的运行时字段。

## 启动为什么又慢又占内存

`catalog.js` 静态导入多个原始数据包，`table()` 在手机上完成解析、解包、跨包去重和合并，再把紧凑数组展开为字段很多的对象。模块顶层立即初始化怪物、物品、法术、任务、掉落索引；随后遍历全世界刷新点，通过距离计算归属地图节点。原始数据与派生对象/索引会同时占用空间。

隔离 Node v24.15.0 进程，仅导入 `engine.js`，没有创建角色和战斗：

- 导入约 3.61 秒（一次桌面样本，不是性能承诺）。
- 导入前 JS heapUsed 约 3.93 MB；导入后约 515.65 MB；主动 GC 后约 **360.36 MB**。
- 合并后已有 14,804 个物品、12,499 个法术、8,539 个怪物、3,837 个任务、66,030 个怪物刷新点。
- 仅将展开后的物品、法术索引再次序列化，就分别约 31.32 MB、37.07 MB；这不是它们的真实堆内存测量，但显示了紧凑行展开后的体积变化。

Node 与 iPhone WebKit 的内存管理不同，这些数值不能当作手机占用；它们足以证明优化必须包含初始化和数据表示，不能只看 gzip 下载大小。

## 按出战职业拆分的限制

1. 当前 `engine.advance` 还调用 `progressNpcWorld`，后台培养约 50 名、覆盖九职业的 NPC。其装备、任务奖励、升级训练和副本奖励查询会用到全局资料。`view` 也会计算 NPC 面板及其他非战斗页面内容。因此当前“单人出战”并不等于引擎只处理一个职业。
2. 法术不是职业独占：宠物、召唤物、图腾、装备触发、消耗品、敌方技能、被控制单位，以及其他职业施加的持续增益都可能引用额外法术。需要递归收集依赖，不能只筛 `classId`。
3. `catalog.js` 和多处规则在模块顶层建立索引、缓存。动态增加数据后，旧派生索引不会自动更新；服务端还需支持多个玩家并发，不能使用“当前职业”这种可变全局状态。
4. 战斗历史最多保留 20 场，且 `projectClientSnapshot` 会复制历史到 UI。这是独立的运行期内存风险，应测量并设字节预算；目前没有证据证明它是此次手机崩溃的直接原因。

## 推荐的数据包边界

| 包 | 内容 | 何时需要 |
|---|---|---|
| 常驻核心 | 通用伤害/治疗/威胁/AI算法、随机数、基础常数、紧凑世界路网 | 引擎启动 |
| 职业/种族 | 实际队伍的技能、天赋、成长、种族能力及递归依赖 | 角色/队伍准备时 |
| 区域 | 当前区域的怪物、AI、任务、交互、掉落与任务依赖 | 进入区域前 |
| 副本 | 当前副本完整路线、首领阶段、召唤物、交互和掉落 | 入本前，避免战斗中等下载 |
| 物品/效果 | 当前装备、背包可用物品、消耗品、附魔与触发效果 | 换装/拾取/使用前，按 ID 或有界分片补充 |
| 专业与城镇 | 当前服务或已学专业所需的操作数据 | 开始相应活动前 |
| 展示资料 | 副本手册、详细说明、本地化、模型和图标索引 | 打开对应页面、显示对应角色时 |
| NPC 养成 | 非出战 NPC 的轻量成长/奖励规则 | 独立于战斗周期，按养成结算边界处理 |

单人任务应加载“核心 + 玩家/宠物/同行者依赖 + 当前区域 + 已有物品/效果”，五人本加载“核心 + 实际出现的职业集合 + 当前副本 + 所有参战单位和物品依赖”。同职业队友不重复加载包。任务可能跨区域，保留轻量全局导航和必要任务摘要，不按阵营裁剪可访问城市和服务。

对 NPC 养成，建议先编译独立的轻量成长、装备候选、奖励池数据，避免读取整个副本手册和全物品扫描；再决定由服务端在养成节点结算，还是浏览器按需计算。无论放在哪里，都必须保留现有成长、收益和随机语义，不能通过停掉 NPC 养成来假装实现裁剪。

## 实施顺序

### 第一阶段：从源资料编译运行时资料

- 保留导入源用于审计，生成独立 runtime 目录；模拟器不再直接 import 原始 reference 文件。
- 在构建机完成去重、覆盖优先级、共享掉落分类、任务关联、刷新点归属、职业获取条件、NPC 奖励池与索引生成。
- 保留已确认规则所需字段；字段裁剪必须覆盖动态访问和技能效果分支，不能仅靠搜索某字段是否出现。
- 分开运行时数据与手册/模型/翻译；避免生成全副本展示对象后再丢弃。
- 第一阶段仍可提供完整 runtime 数据，先用全量行为对照验证编译结果，再做分片，避免同时改变规则与加载时序。

### 第二阶段：显式目录与活动依赖加载

- 引擎接收只读 `RuleCatalog` 上下文，撤掉导入时全局建表。服务器和浏览器使用同一编译产物和算法，服务端目录允许并发安全复用。
- `prepareActivity(state, command)` 在开始模拟前算依赖闭包：技能触发链、召唤物、装备效果、嵌套掉落表、任务奖励与交互都要包括；处理环依赖并校验缺项。
- 获取并校验所有所需包后一次性安装目录，再开始/继续确定性的同步 tick。不要在伤害计算中临时 await 网络。
- 副本整包预取；旅行预取目的地；更换队员、换装、接受跨区任务触发补载。升级、驯服、召唤等自动变化也应在可确定的边界预备依赖。
- 下载失败保留当前状态并暂停，不以空表或默认伤害继续推进。加载等待和补算遵循现有服务器锚定时间、离线额度、租约及检查点协议。
- 包清单绑定统一 `contentVersion` 与内容 hash，原子切换，防止缓存把两套规则拼在一起；不做旧格式兼容层。

### 第三阶段：内存预算与验证

- 大型数据用可释放的 JSON/紧凑数据包，不只把静态 import 改成 dynamic import。后者会缓存已加载模块，游历多个区域后仍可能积累数据。
- 当前战斗、装备、活动效果和检查点所引用的数据固定保留；其余包按字节预算淘汰，同步清理派生索引。浏览器磁盘缓存和活跃内存缓存分别管理。
- 战报按字节预算保留，普通快照发摘要，用户查看时再取详情；减少 Worker 与主线程重复持有历史。
- 在创建角色、首场战斗、连续 30 场战斗、跨区/换队、五人本、25 人团本、后台恢复、网络失败和版本切换上验证。对照固定种子下的战斗、AI、掉落、NPC 成长和存档状态，确保加载策略不改变结果。
- 指标同时记录冷/热启动耗时、各包传输/解压大小、Worker/主线程内存趋势、消息峰值和加载失败恢复。单职业任务验收时，网络请求中不应出现无关副本/全职业/全世界原始包；连续换图后的常驻内存应趋于稳定。
- **最终稳定性必须由 iPhone Edge 连续游玩验证**。本报告不预先承诺优化后 MB 数值或绝不崩溃；应先实现一条“单人任务 + 五人本”完整加载链再量化收益。

## 复现与代码入口

```sh
node scripts/audit-local-simulation-payload.mjs > /tmp/local-simulation-payload.json
node --expose-gc scripts/audit-local-simulation-payload.mjs --memory
# 可选：分析本地生产构建实际生成的共享 chunk（hash 会随构建改变）
node scripts/audit-local-simulation-payload.mjs --shared-chunk apps/web/.next-audit/static/chunks/9531.cd0efcdca6d24fd2.js
```

- `apps/web/lib/local-simulation.worker.ts`：完整引擎入口、周期快照和战斗帧。
- `packages/game-domain/src/rules/catalog.js`：原始数据导入、运行时合并、展开、全世界索引。
- `packages/game-domain/src/rules/dungeon-journal.js`：全副本手册初始化、共享掉落判定、展示依赖。
- `packages/game-domain/src/rules/npc-world.js`：全职业 NPC 养成、全物品扫描和手册奖励查询。
- `packages/game-domain/src/rules/client-snapshot.ts`、`combat-metrics.js`：历史战报保留与复制。
- `scripts/compile-game-data.mjs`：当前主要负责校验和版本 hash，尚未编译上述运行时分片。

本次研究的生产构建通过；构建临时注入的统计插件及 Next 自动增加的 tsconfig 路径已还原。测量脚本只读内容并在内存打包，不改线上存档或部署。
