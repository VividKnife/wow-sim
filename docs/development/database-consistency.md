# 数据一致性与后台模拟

## 按操作划分，而非按整张表降低隔离级别

| 路径 | 一致性与提交策略 | 可以接受的滞后 |
| --- | --- | --- |
| 装备、背包、金币、经验、任务奖励、购买/出售、制造预留与结算 | `Store.transaction`：SERIALIZABLE，完整回滚和有限退避重试；资产、角色进度、receipt、ledger、settlement 在同一事务提交 | 不允许重复发奖、透支、丢失已提交进度 |
| 存档列表、权限查询、角色快照、回放读取、worker 到期扫描 | `Store.read`：REPEATABLE READ READ ONLY；接口不提供写操作，PostgreSQL 同时禁止写入 | 本次读取后发生的更新可以等下次刷新 |
| 在线心跳 | 独立 `account_presence`，READ COMMITTED 原子条件更新；时间单调递增，通常每秒最多写一次 | 亚秒级在线时间精度不作为资产正确性条件 |
| 长时间离线后重连 | 仍为关键事务：更新时间锚、恢复调度、失效旧模拟、必要时增加账号 revision | 不能通过重连重复计算离线收益 |
| 个人活动/副本后台推进 | 读取一致输入 → 释放数据库连接 → 确定性计算 → 短事务校验并结算 | 过期或冲突的模拟直接丢弃，下轮调度重算 |
| 战斗回放预计算 | 事务外计算；发布时校验 owner 和参与账号版本；领取结果另行原子结算 | 回放可以晚一轮出现，不能提前发放未来奖励 |

`characters.rules` 同时包含血量、位置、经验、等级、任务进度等字段。不能把整张角色表或整个“战斗更新”改为无保护写入。看似只是修改策略的玩家命令，也可能先推进战斗、获得经验或消耗弹药，因此命令当前保留关键事务。

## 具体边界

- 账号的 `revision` 只表示权威游戏状态版本；`lastSeenAt` 已从账号移到独立的 `account_presence`。普通心跳不增加 revision，也不覆盖账号记录。
- 心跳只 UPDATE 已存在的 presence，不能重新创建已删除的存档数据。超过重返在线阈值或离线收益时限时，回到领域事务处理，不能直接更新时间掩盖超时。
- 快照组装只读。空闲角色恢复先从快照发现到期角色，再单独事务重新检查其执行租约、提交恢复，之后重新读取快照。重复查询已恢复的角色不产生写入；恢复提交遇到事务竞争时仍返回已提交快照，下一轮查询再尝试。
- 后台计算输入使用只读快照。计算期间不占数据库连接，也不持有 SERIALIZABLE 事务。
- 后台结算校验活动/副本完整输入记录和参与账号的权威记录。副本另外校验 worker、epoch 与租约有效期。其他命令、结算或存档重建胜出后，旧结果不能覆盖新状态。
- 所有会影响角色、资产或模拟输入的新增领域写入，必须同步增加相应账号 revision；涉及副本时还需更新副本 sequence/模拟版本。账号 revision 是后台输入有效性的明确约束，不能绕过。
- 校验与资产、经验、进度、结算凭据的写入处于同一个 SERIALIZABLE 事务。重复 worker 不能分别成功提交同一个结果。
- 后台模拟提交、回放发布和副本租约竞争仅尝试一次，冲突后让出执行权。玩家关键操作保留最多 9 次尝试，避免非关键模拟反复阻塞工作队列。
- 最终的序列化冲突和死锁返回 `DATABASE_BUSY` / HTTP 503；不再包装成 `RULE_REJECTED` / HTTP 400。连接或 SQL 操作失败单独包装为 `DATABASE_FAILURE`，保留原始 cause 供排查；原始数据库错误不直接展示给玩家。

副本在异常路径也会尝试释放租约；如果释放遇到竞争，原有租约到期机制负责恢复。后台模拟采用有界计算，不要求一次 worker 调用完成所有离线战斗。

## 验证与开发数据

`packages/persistence/test/postgres-concurrency.test.ts` 使用真实 PostgreSQL 多连接，每次创建随机独立 schema，结束后只清理该 schema。设置 `POSTGRES_TEST_URL` 后运行：

```powershell
node --test packages/persistence/test/postgres-concurrency.test.ts
```

覆盖并发查询/心跳与资产写入隔离、只读快照稳定性、并发扣款与幂等、重复 worker 奖励结算、心跳单调性与删除后不复活。没有配置测试 URL 时这些测试会明确跳过，PGlite 测试不能替代真实多连接验证。

领域测试另外覆盖玩家命令与模拟竞争、旧结果丢弃、离线暂停/恢复、数据库重启后的制造收益只领取一次，以及数据库错误分类。

本次改变存储结构。旧存档缺少 `account_presence` 时视为无效开发数据，需要删除并重新创建；不提供旧字段回退或迁移。开发数据库未被自动清空。server 与 worker 必须运行同一版代码。

这些检查证明所测并发交错下的正确性，不代表完成了容量或吞吐量压测。剩余成本包括完整角色 JSON 检查点、资产差异计算、需要结算的前台命令及共享副本的关键提交；这些路径继续使用事务保护。

参考：[PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)、[序列化失败处理](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html)。
