## 修改

- 在线战斗结算、战斗窗口轮询目标周期均为 200 ms；worker 到期扫描默认 100 ms。无在线观察者时恢复 1000 ms 结算周期。
- `/game?scope=combat` 保留公开 player 状态，仅生成战斗 view。减少反复生成和传输训练、地图、天赋、经济、策略技能列表的开销。非战斗返回完整响应；客户端不允许跨角色、跨内容版本合并。
- 轮询串行执行，有超时、卸载取消、后台暂停和前台恢复。取消信号经 Web 代理传递至游戏服务请求。完整/战斗响应的 ETag 分开。
- Pixi 完整特效最高 60 FPS、简化特效最高 30 FPS；弹道时钟在帧内推进。HUD 10 Hz，进度条与单位位置连续过渡，显示时间不回退。命中和生命值仍以权威状态为准。
- 排布按快照/缩放缓存，网格只在比例变化时重绘；统计面板跳过纯计时重渲染，策略首次展开后才挂载并保留编辑草稿。异步渲染器加载完成时立即接收最新场景。

## 测量

使用内存中的 20 级五人小队、3 个敌人，不读取玩家存档。

`node scripts/benchmark-combat-sync.mjs`，各模式预热 5 次，测量 48 次。响应体为未压缩 UTF-8 字节，时间仅包含响应构造，不包含数据库与网络：

| 指标 | 完整快照 | 战斗快照 |
| --- | ---: | ---: |
| 响应体 | 488,942 B | 44,636 B |
| 平均构造耗时 | 26.19 ms | 1.77 ms |
| P95 构造耗时 | 28.48 ms | 2.19 ms |

响应体减少约 91%，构造耗时减少约 93%。此前探索测量使用字符串长度，以上 UTF-8 计量为最终口径。

浏览器夹具：运行 `node apps/web/scripts/serve-dungeon-preview.mjs`，打开 `/combat-upgrade.html`，点击“开始 12 秒性能采样”。关闭“简化特效”，自动取景，未展开策略。在同一开发浏览器两次采样中：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| Battle React 提交次数 | 292 | 197 |
| React 总渲染耗时 | 1423 ms | 650 ms |
| 最慢 React 渲染 | 14 ms | 10 ms |
| rAF 最大间隔 | 63 ms | 32 ms |
| rAF P95 间隔 | 14 ms | 15 ms |

React 渲染耗时减少约 54%。rAF 测量是浏览器回调间隔，不等于 Pixi 实际 FPS，也不构成所有设备稳定 60 FPS 的保证。夹具仍在浏览器中运行真实引擎和完整 view，采样不代表生产网络端到端延迟。

## 真实账号冻结回归（2026-09-17）

`dungeon20` 在完整特效下开战约 4 秒后停止更新；数据库实例序号也连续停止，浏览器没有错误。高频 snapshot 在同一个 SERIALIZABLE 事务中写 presence 并读取完整角色/背包/实例，使读取轮询与 worker 结算相互冲突。修复将在线心跳独立成短事务，最多每秒更新一次（短离线窗口使用窗口的四分之一），随后单独读取快照。在线积压模拟每事务最多 20 ticks，提交中间进度后继续追赶，避免长事务反复重算；非个人生产任务保留原预算。

修复后原战斗完成；下一场完整特效战斗超过 30 秒仍持续推进，连续 8 次一秒间隔数据库采样均有新序号，模拟时间落后实时时间约 0.2–0.4 秒。此验证证明冻结恢复，不代表所有设备稳定 60 FPS。未清空账号或改写存档。

后续可将实时战斗改为服务端单实例内存推进、约 200 ms 发布快照、5 秒持久化检查点、结束时原子结算奖励。该方案尚未实现；必须同时调整指令路由、实例归属、重启恢复和结算幂等性，不能仅降低数据库写入频率。
