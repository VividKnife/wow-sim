# 战斗实时更新优化验证

## 持续战斗数据流与 UI 修复（2026-09-23）

用户反馈多种战斗持续卡顿，简化特效也无明显帮助。本轮用正式 `local-simulation.worker.ts`、`publishLocalCombat` 和完整 Battle 界面复测持续推进的战斗。

### 原因与修改

- Worker 原先每秒调用一次完整 `view`，其中包含技能、天赋、背包、训练师和 PvP 配置。在 25 人样例中，该投影平均耗时 681 ms，战斗数据到达间隔 P95 为 719 ms。战斗窗口原本会丢弃同一场战斗的完整更新；现在观察战斗时直接省去这项计算，在开战、结束、换场、命令检查点以及关闭战斗窗口时提供完整快照。团本状态另行每秒更新，战斗帧同时报告追赶状态。
- Worker 50 ms 调度现在包含本轮计算耗时，避免计算完成后额外再等 50 ms，拉长战斗数据周期。离线结算和手动命令仍使用原来的有界计算与权威检查点。
- 每个角色、每个伤害数字原先单独创建 Drei `Html` 根节点。新伤害出现时反复遍历整棵 Three 场景，数据更新又引发许多独立 React 提交。现在整场战斗共用一个 DOM 层；标签逐帧投影使用与模型相同的插值位置和镜头。
- 模型组件只在外观、选择、阵营显示、死亡和移除等相关变化时重新协调，位置和动作从逐帧数据读取。命中特效复用组件，避免数据包到来时反复构造几何树。实时和录制回放的投影均按数据包缓存，HUD 的额外提交不再重建布局、打断位置插值。
- `spellInfo` 的百分比耗蓝直接读取职业／等级基础法力，避免每个技能重新计算整张角色属性表。装备、光环、天赋仍按原规则影响实际属性和技能；相同 100 个模拟步骤的完整状态与战斗帧哈希逐一一致。完整 `view` 的平均耗时也从 681 ms 降到 396 ms。

### 持续战斗采样

同一台机器，Chromium 无头浏览器，Vite 开发预览，1440 × 1050、DPR 1。Canvas 就绪后预热 5 秒，采集 12 秒 rAF、主线程 CPU profile、长任务和 Worker 消息；模拟全程继续运行。团战采用 MC demo 的真实 25 人队伍和卢西弗隆；野外和五人队使用独立测试角色，并增加敌人生命以覆盖完整采样时段。夹具不连接或修改存档。

| 场景 | rAF P95 | rAF 最大间隔 | 主线程长任务 | 战斗帧到达间隔 P95 |
| --- | ---: | ---: | ---: | ---: |
| 25 人精细，修复前 | 62.6 ms | 125.1 ms | 26 | 718.9 ms |
| 25 人精细，修复后 | 41.7 ms | 62.5 ms | 0 | 129.3 ms |
| 25 人简化，修复后 | 27.8 ms | 55.6 ms | 0 | 131.2 ms |
| 五人队精细，修复后独立复测 | 20.9 ms | 132.0 ms | 1 | 127.4 ms |
| 野外精细，修复后 | 20.9 ms | 27.8 ms | 0 | 125.7 ms |

25 人精细模式的 rAF P95 下降约 33%，战斗数据间隔 P95 下降约 82%。各场景在 12 秒采样中都推进约 12 秒模拟时间。五人队仍有一次新模型首次绘制时的着色器编译长任务（约 134 ms），CPU profile 定位到 WebGL `getProgramInfoLog`；本轮没有消除该类首次加载停顿。rAF 是浏览器回调间隔，简化模式的 Canvas 按需绘制，不能由 rAF 次数推断实际 GPU 帧率，也不代表所有设备稳定 60 FPS。

复现：运行 `node apps/web/scripts/serve-dungeon-preview.mjs`，打开 `/battle-live.html?mode=raid`，也可切换 `mode=dungeon` 或 `mode=solo`。浏览器 Performance 面板录制预热后的持续战斗。原始采样、截图和 CPU profile 位于本地 `.cache/battle-live-performance/`，其中 `before-raid`、`final-raid`、`final-raid-low`、`verify-dungeon`、`final-solo` 对应上表；`compute-before/after.json` 包含模拟逐步哈希。

验证：117 项相关测试通过；根项目和 Web TypeScript 检查通过；内容 manifest 已重建且 `data:check` 通过。定向 ESLint 无错误（既有 `any` 文件关闭 `no-explicit-any` 检查），保留图标 `<img>` 和录制回放 effect 依赖两项既有类型的提示。新增覆盖完整快照延后与恢复、换场、离线命令、调度周期、实时／录制投影稳定性、标签插值同步，以及等级、装备、诅咒和宠物对耗蓝的影响。

浏览器交互复查通过标签键盘选择、缩放及自动取景、精细／简化特效切换、拖动镜头及恢复自动镜头、关闭后重新打开战斗；无页面运行错误，已检查实际战斗截图。更新后需刷新游戏页面，创建使用新代码的模拟 Worker。

## 3D 骨骼与资源加载修复（2026-09-23）

本次修改共用的 `BattleHD2D` 渲染链路，适用于野外、副本、团队和竞技场，不改变模拟步长、伤害或战斗结果。

- `SkeletonUtils.clone` 会为每个网格分块克隆骨骼。人类男性身体有 56 个分块、119 根骨骼，原实现为这些分块保留 56 份相同的骨骼矩阵。`createCreatureInstance` 现在按源 skin 合并为每角色一份；不同角色、不同 skin 仍保持独立。Three 每帧只需更新和上传一份共用矩阵。
- 出场时不再为全部 20 个动作预先创建 AnimationAction 与轨道绑定，改为首次使用时创建并复用。相同皮肤只在纹理配置变化时标记上传，不再按身体分块、角色重复标记。
- 角色模型使用独立 Suspense 边界。新召唤物、变形或换外观所需的资源尚未加载时，现有战场与其他角色继续显示，待加载角色保留可选择的状态标签。
- 地形装饰和后处理组件使用 memo，避免每次生命值／时钟更新重复遍历静态组件树。其逐帧动画和画质切换仍然生效。

在同一台机器、Chromium 无头浏览器、1440 × 1050、DPR 1、精细特效下，使用 `/battle-3d.html` 的 MC 25 人场景采样。资源就绪后暂停试玩模拟，预热 3.5 秒，记录 8 秒 rAF 间隔及浏览器 CPU profile，隔离绘制成本：

| 指标 | 修复前 | 骨骼修复后 | 最终版本复测 |
| --- | ---: | ---: | ---: |
| rAF P95 间隔 | 27.8 ms | 20.9 ms | 20.9 ms |
| rAF 最大间隔 | 69.4 ms | 48.7 ms | 69.4 ms |
| 超过 50 ms 的主线程长任务 | 1 | 0 | 1 |

两次修复后采样的 P95 均降低约 25%；最终复测仍有一次长帧，不能宣称已消除所有偶发卡顿。

这是暂停模拟后的渲染采样，不能当作实时战斗端到端帧率或所有设备稳定 60 FPS 的保证。该试玩页面将 `advance` 和完整 `view` 放在主线程每 100 ms 执行；不暂停时，本次测到 636 ms 的主线程长任务，CPU 热点包括天赋、技能和属性投影。正式游戏通过 `local-simulation.worker.ts` 执行这些计算，所以不能直接用这个试玩页的运行中采样推断正式游戏绘制成本。

## 修改

- 在线战斗结算、战斗窗口轮询目标周期均为 200 ms；worker 到期扫描默认 100 ms。无在线观察者时恢复 1000 ms 结算周期。
- `/game?scope=combat` 保留公开 player 状态，仅生成战斗 view。减少反复生成和传输训练、地图、天赋、经济、策略技能列表的开销。非战斗返回完整响应；客户端不允许跨角色、跨内容版本合并。
- 轮询串行执行，有超时、卸载取消、后台暂停和前台恢复。取消信号经 Web 代理传递至游戏服务请求。完整/战斗响应的 ETag 分开。
- Pixi 完整特效最高 60 FPS、简化特效最高 30 FPS；弹道时钟在帧内推进。HUD 10 Hz，进度条与单位位置连续过渡，显示时间不回退。命中和生命值仍以权威状态为准。
- 排布按快照/缩放缓存，网格只在比例变化时重绘；统计面板跳过纯计时重渲染，策略首次展开后才挂载并保留编辑草稿。异步渲染器加载完成时立即接收最新场景。

## 真实账号冻结回归（2026-09-17）

`dungeon20` 在完整特效下开战约 4 秒后停止更新；数据库实例序号也连续停止，浏览器没有错误。高频 snapshot 在同一个 SERIALIZABLE 事务中写 presence 并读取完整角色/背包/实例，使读取轮询与 worker 结算相互冲突。修复将在线心跳独立成短事务，最多每秒更新一次（短离线窗口使用窗口的四分之一），随后单独读取快照。在线积压模拟每事务最多 20 ticks，提交中间进度后继续追赶，避免长事务反复重算；非个人生产任务保留原预算。

修复后原战斗完成；下一场完整特效战斗超过 30 秒仍持续推进，连续 8 次一秒间隔数据库采样均有新序号，模拟时间落后实时时间约 0.2–0.4 秒。此验证证明冻结恢复，不代表所有设备稳定 60 FPS。未清空账号或改写存档。

后续可将实时战斗改为服务端单实例内存推进、约 200 ms 发布快照、5 秒持久化检查点、结束时原子结算奖励。该方案尚未实现；必须同时调整指令路由、实例归属、重启恢复和结算幂等性，不能仅降低数据库写入频率。
