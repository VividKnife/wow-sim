## 一致性范围修订（2026-10-01）

用户明确要求尽量参考 AzerothCore 的事务/一致性做法，避免额外的一致性复杂度和性能损耗。
此要求优先于本文早期对完整输入日志、广泛强确认和分布式恢复的扩展设想。
采用内存单写者、按业务边界批量保存和普通数据库事务；不新增全事件持久化、跨服务两阶段提交、
实时副本复制或以零画面回退为目标的恢复协议。已提交资产和实例归属仍需防止重复应用。
具体实施边界及尚未移除的成本见 [数据一致性](database-consistency.md)。

## 后续决策：玩法灵活性、团队指挥和空间规则（2026-10-01）

用户后续意见进入同一个重构目标：允许提升 NPC 决策；优先服务器性能和扩展边界；
客户端性能优化后置；支持未来增加其他资料片规则；副本采用清楚的碰撞、视线和导航职责。
以下是实施约束，不能将设计接口视作已经交付的多版本、导航网格或通关能力。

### 团队指挥与 Boss 机制分工

采用“遭遇定义 + 玩家作战计划 + 通用团队执行器”。开发者仍编写 Boss 的技能、阶段、
召唤、可观察提示、场地变化和胜负条件；新增机制也可能需要新增通用执行能力。
不以给每个 Boss 写一套私有 NPC 通关逻辑作为主要扩展方式。

作战计划包含成员/职责/小队选择、坦克目标与朝向、集合点/分散距离、集火与控制、
驱散/打断轮换、治疗和防御技能安排。触发条件只使用已经公开的施法、光环、阶段、
生命资源阈值和玩家口令。默认计划可编辑，玩家实时命令能覆盖自动计划；
撤销、失效、负责人死亡和接替均有明确优先级及回执。NPC 不读取未来事件或隐藏随机结果。
计划失效时报告不可达、超出射程、被遮挡、冷却或负责人失效，不能瞬移或跳过技能校验。

奥妮克希亚脚本负责深呼吸轨迹、火球、雏龙与阶段变化；玩家决定坦克位置、
两侧分组、接怪、集火、移动纪律与技能保留。通用执行器完成可达站位、
路线跟随、分散、援护及已分配技能，而不是按 Boss ID 调用一段“必胜 AI”。
平面开放龙巢中的深呼吸主要需要危险区域和团队指挥，不因引入导航网格自动得到更好战术。

Playerbots 的策略/触发器/候选动作分层可作为实现参考，不能直接推导其策略在本项目更优；
以不同阵容、机制处理、死亡、资源、完成率和 CPU 实测评估策略改进。
[Engine 定义](https://github.com/mod-playerbots/mod-playerbots/blob/master/src/Bot/Engine/Engine.h)

### 空间层采用 vmap/mmap 的职责，不依赖其文件格式

AzerothCore 的碰撞接口提供视线、命中位置与高度查询，导航接口负责可达路径；
地图层同时考虑静态与动态遮挡。其提取工具面向原客户端地图，本项目不引入那套数据依赖。
[VMap 接口](https://www.azerothcore.org/doxygen/da/d58/classVMAP_1_1IVMapMgr.html)、
[地图视线查询](https://www.azerothcore.org/doxygen/d7/db0/classMap.html)、
[PathGenerator](https://www.azerothcore.org/doxygen/d3/d93/classPathGenerator.html)

| 层 | 本项目责任 | 不应混入的规则 |
| --- | --- | --- |
| 场景几何 | 本地边界、障碍、未来的楼层/高度和连接 | 职业循环、Boss 策略 |
| 碰撞与视线 | 路段通行、目标遮挡；移动与视线分别配置 | 将火圈视为不可穿越墙壁 |
| 导航 | 可达路径、合法终点、缓存失效、有界计算 | 自动选择全团最优战术 |
| 危险区域 | 生效时点、形状、伤害、移动代价与承伤安排 | 直接改写静态导航图 |
| 团队执行 | 把玩家站位/分工转成合法意图；按角色选择是否绕险 | 读取未公开的未来机制 |

先用现有自定义局部场景实现二维几何和路径服务。复杂房间需要多边形通行区；
多层、桥梁和斜坡需要显式楼层/高度与连接，不能将两个重叠楼层按二维距离互相攻击。
首个房间用构建时生成的简单多边形三角网格；复杂三维场景是否采用 Recast/Detour
由地图复杂度和剖析决定，不将某个库或原版 vmap/mmap 二进制格式作为首版前置条件。
飞行、跳跃、冲锋、击退、投射物、持续范围效果各自有规则能力与碰撞策略；
不能将所有效果无差别套上地面寻路或每跳视线校验。

#### Boss 房体验与绘制的实施方向（2026-10-01 复核）

本轮实现前，`combat-area.js` 只接受矩形与最多 32 个圆形障碍；`scene-space.js` 在膨胀圆形周围建立
可见图，提供二维绕路与视线。前端 `battle-hd2d/environment.tsx` 主要按主题生成地面与装饰，
`obstacles.tsx` 才将部分权威圆柱画出来。它们不构成完整 Boss 房几何或原版地图复现。

Boss 房作为正式的版本化场景资源，优先替换通用矩形房间。目标是一个创作来源产生三类产物：

- 服务端碰撞几何：可行走边界、墙体/柱体、视线遮挡、高度查询以及动态门的状态引用。
- 服务端导航数据：预生成的通行多边形与邻接关系、单位体型限制、明确的跨层连接；复杂场景再选择
  Recast/Detour 等烘焙后端，不要求 Node 热循环实现网格生成或读取 AzerothCore 二进制。
- 客户端绘制资源：地面、墙壁、巢穴、熔岩与装饰模型，使用同一坐标、比例、场景 ID 和几何版本。
  碰撞模型可以简化，关键通路和边界必须与可见场景一致；纯装饰明确不参与碰撞。

先以奥妮克希亚房间验证边界、两侧增援入口、Boss 朝向、空中位置和深呼吸路线；随后以拉格纳罗斯
验证熔池、可站立区域及承伤/绕行。位置改动作为玩法变更重新验收，不把美术调整隐式当作原规则等价优化。
房间公开语义点保存入口、集结区、召唤位置、阶段位置和允许的飞行段，脚本引用语义点，避免把坐标散落在
Boss AI 与前端中。飞行使用独立运动能力；不能给地面路径查询传入悬空目标后强制穿墙到达。

危险区域仍是时变遭遇状态，可以影响 AI 路径代价或玩家指挥下的承伤选择，不因每次火圈变化重建静态导航。
开发者定义 Boss 独有机制与阶段，通用团队框架执行坦克位置、面向、散开、集合、增援接管和玩家口令。
导航只回答怎么走，不决定玩家应该采用哪套战术。保留已有反应窗口和角色能力边界。

静态索引在 Worker 内共享，按需查询和缓存路径；门/通路变化使相关路径失效。衡量每场遭遇的寻路次数、
最坏查询耗时、内存和调度延迟，不把引入导航网格本身当作性能提升证明。客户端只加载当前场景资源，
绘制优化与权威空间实现可分别迭代。内容资源与规则包分别版本化，未来版本可以复用空间引擎而替换场景/机制。

验收至少包括贴墙移动、绕柱视线、不可达目标、不同体型通过窄路、动态门、击退边界、宠物跟随、
深呼吸显示与实际伤害区域一致，以及 40 人含召唤物的路径突发负载。高度/跨层功能落地时再增加相应场景验收。
这节是实施方向，尚未生成新 Boss 房资源或接入新的导航后端。

参考：[AzerothCore 碰撞接口](https://raw.githubusercontent.com/azerothcore/azerothcore-wotlk/master/src/common/Collision/Management/IVMapMgr.h)、
[PathGenerator](https://www.azerothcore.org/doxygen/d3/d93/classPathGenerator.html)、
[静态树与导航数据共享](https://www.azerothcore.org/doxygen/d6/db7/classMapCollisionData.html)。

静态几何及索引在同一 worker 内按内容版本共享；实例保存门、平台等动态状态及版本。
路径以目标和空间版本失效，已开始的路径和输入顺序纳入恢复语义。
不对每个 Bot 每 100ms 重建图，不在每个实例复制客户端场景模型。
验收包括绕柱、门状态变更、不可达目标、窄通道、墙后治疗/攻击、途中被控制、
已发射投射物与已施加 DOT 的明确规则，以及同一快照恢复后的移动时间线。

Boss 场地的实施顺序按实际机制决定：开放龙巢先提供边界、危险带与站位点；
存在柱子和拐角的房间需要绕障与遮挡；桥梁、上下层和平台进入内容后再加入分层导航。
导航描述“能否走到”，危险代价描述“何时经过会受伤”，团队任务描述“为什么去那里”。
例如深呼吸的安全终点不能保证整条路线安全，需要按预计经过时刻检查公开危险区域；
承伤任务也不能被一律避险的移动规则覆盖。动态门关闭则是真实通行变化，应使相关路径失效。

路径请求应返回到达、部分路径、不可达或预算待处理等明确结果；部分路径不能宣称已完成站位。
预算耗尽时保留合法执行位置并重试，不瞬移、不沿穿墙直线回退。
未来导航能力需区分单位半径及地面/飞行等移动能力；当前二维实现使用固定半径，尚未实现这些能力。
地图几何与规则包分别版本化，副本内容绑定二者；相同几何可以被不同规则包复用，
但不能默认不同资料片的门状态、飞行规则和技能遮挡规则也相同。

### 哪些数据驻留内存

狩猎、战斗、活动中的角色/NPC、位置、施法、临时光环、属性缓存由实例单写者驻留。
跨地区旅行继续使用节点和到达期限；没有玩家活动的地区不需要常驻全部 NPC。
物品/附魔/天赋的静态定义共享只读加载，角色所用配置在活跃实例中缓存并按版本失效。
换装、天赋变更和附魔经 owner 有序验证，再按业务边界事务提交。
拍卖检索可用索引或缓存，挂单、竞价、成交、钱物归属仍以事务和幂等提交保护；
内存驻留不意味着全部经济数据由战斗线程独占，更不意味着全部 NPC、拍卖单进入 tick。

Entity 借鉴身份、生命周期、单位能力、物品归属和场景上下文分离，采用组合式职责，
不逐层复制 AzerothCore 的继承树。真人与 NPC 共享 Character 身份/成长和 Unit 战斗能力，
控制器独立；物品用永久 ItemInstance ID；拍卖、任务与旅行用各自业务实体，不伪装成 Unit。

### 资料片规则与实施优先级

实例固定 rulesetId、规则修订、内容哈希和空间版本。跨版本相同数字 ID 不代表同一技能；
命中表、资源、天赋、光环刷新、技能队列、能力集合与装备政策可以由不同规则包实现。
通用调度、实例归属、持久化和导航不硬编码 Classic/3.3.5a；团队计划按能力寻找施法者，
资料片适配器解析具体技能。不能仅替换数据表就声称支持新资料片。
用户提到的未来版本名称和具体目标数据集待实际扩展时确定，不影响现在建立规则隔离。

下一阶段以通用执行边界、实际战斗事件化、独立角色/资产、规则包和空间服务为主线，
团本回放用于暴露基础能力缺口。仍须完成用户要求的网页狩猎、任务、五人 Boss 和
奥妮克希亚击杀、掉落、分配全流程；客户端优化后置不等于取消可用性与网页验收。

### 本轮落地与剩余边界

`sim-core/src/scene-space.js` 从本仓库原有竞技场几何实现重构，没有复制 AzerothCore 代码。
竞技场地图定义独立到 `arena-maps.js`，删除原 `arena-space.js` 及其 API。
通用空间层已接入 PvE/PvP 普通移动、目标技能起手/完成、治疗、常规近战及敌人普通施法。
单位不再保存整份 `arenaArea`，技能与观察决策显式从所属战斗读取空间上下文。
圆形障碍分别配置 `blocksMovement` / `blocksSight`；路径和图缓存按导航版本失效，
每场景最多 32 个圆形障碍以限制当前可见图规模。这个限制是本实现边界，不是游戏并发容量。

路径进度可序列化；决策试算不会原地消耗共享路径数组；新遭遇重置个人路径。
现有投射物和已施加的持续效果保持各自规则，没有在每次伤害上强加视线查询。
尚未新增任何副本障碍布局，也未实现多边形导航网格、高度层、平台/门玩法、
动态危险代价寻路或完整的不可达命令回执。当前路径缓存按场景对象共享图，
不是已经完成跨实例的不可变空间内容注册器。

新增空间测试覆盖遮挡/通行独立、PvE 绕障、序列化恢复、导航版本失效、
墙后伤害与治疗校验、敌人施法期间遮挡变化和内容规模校验。
空间/输入/分散/坦克/治疗组合回归 50/50 通过；竞技场、战场、战斗策略、指挥、
敌人周期效果与团本场地组合回归 78/78 通过；类型检查和网页构建通过。
网页构建仍有既有大 chunk 提示；没有将编译通过记录为新的网页玩法验收。

当时发现团队指挥中的具体问题：`raidCommandTick()` 的恐慌触发直接读取 `nextFear`。
这项读取及公开面板暴露远期随机机制计时的问题已在下述“团队条件与公开预警”中处理。
推荐计划、技能分工和复盘仍含首领/技能专用逻辑，完整通用计划与能力映射尚待继续迁移。
此前本地奥妮克希亚诊断回放在通用治疗/援护/分散调整后到达第三阶段，
266.432 秒团灭、首领剩余 34%。这是回放诊断，加入了显式集火命令和新编队字段，
不是原样回归或网页通关；掉落与分配验收仍未完成。

### 团队条件与公开预警（2026-10-01）

`bot-ai/src/team-condition.js` 提供预编译的血量阈值、资源阈值、可见效果、
已公告机制预警和手动触发条件。条件仅接收当前时间、负责人目标的公开生命资源、
机制来源的可见状态和预警；不接收实例、未来队列或首领脚本。
Classic 团本的盾墙、圣疗和激活安排已使用这些条件，仍走原有统一技能验证和消耗入口。
预警匹配要求来源存活、机制类型一致、已公告且未过期，不能用未公告的私有计时触发。

遭遇脚本的 `publishRaidWarnings()` 将临近两秒内的已安排机制发布为公开提示。
提示包含来源、机制类别、公告时间和生效时间；玩家面板和 NPC 观察共享同一提示。
`raidNextMechanics()` 现在只投影已公告提示，不再直接读取或公开完整未来计划。
过期、阶段切换后被撤销和来源死亡的提示会移除；发布不消耗 RNG，检查点保留公告状态。
这是有意增加的公开预警窗口，不能描述为纯内部性能优化或原行为完全不变。
地图火区与深呼吸轨迹继续由已有可见区域机制发布，不预先揭示尚未抽取的随机落点。

指挥器已删除玛格曼达专用的 `nextFear` 读取与恐惧触发的 Boss ID 限制。
玩家可对奥妮克希亚等其他首领安排同一恐惧预警条件；没有预警时不会凭内部时间发动。
网页选择器同步改为“收到恐惧机制预警时”和“首领出现可驱散激怒时”。
当前可见激怒由 Classic 的光环驱散类别映射，具体技能仍是 Classic 适配；
这不等于已经完成跨资料片能力注册或任意团队计划编辑器。

### 战斗引导与可取消事件索引（2026-10-01）

奥术飞弹、暴风雪、职业引导、驯服与精神控制现在通过同一战斗注册入口创建引导记录。

中断、死亡、替换后旧引导不能产生后续效果，已经发射的投射物仍保留自己的生命周期。

受击缩短可能使结束时间早于原唤醒，因此堆增加按稳定事件序号的索引取消，删除成本 O(log n)。

检查点保存引导结束时间、下一跳位置、关联事件序号和就绪状态；

脱战引导与其他活动、战场简化治疗、普攻、光环、恢复和遭遇计时仍须继续迁移。
引导期间的射程/目标失效检查仍借助现有 100ms 规则步；后续应由空间和状态变化定向唤醒。
本轮没有完成整体事件预算让出，也没有新增网页通关验收。

### 1. 最小可靠性边界必须提前到 B

原计划把完整恢复列为 E 是合理的，但 B 开始拥有真实资产之前，至少必须有：

- 持久 owner/epoch/租约；旧 owner 的所有提交与对外发布都被 fencing。
- 输入回执区别 applied 与 durable，明确允许回退的范围。
- 检查点和业务提交具有稳定的序号；重启不更换业务幂等键。
- 数据库超时、队列容量和本地执行权到期后停止继续产生权威结果。

否则“先放进内存，后补恢复”会制造已经发放资产而检查点尚未到达该位置的窗口。
这些机制已连接个人角色的检查点资产提交，并通过内部 RPC 驱动真实任务与狩猎。
个人角色网页已接入新权威路径；多人资产和完整活动协议尚未完成，不能宣称全玩法切换完成。

### 2. 实例单写者必须覆盖经济命令与两个真人

当前 `GameService.command()`、`persistInstance()`、个人活动、预计算与浏览器检查点都有自己的写入路径。
单独启动一个 Worker 池不会自动使它们失去写权限。上线切换必须同时改变：

1. `actor_leases` 的角色活动占用与 simulation owner 的关系。
2. 换装、天赋、物品使用、补给、GM、退出、重置等全部写入入口。
3. 全体成员的身份、钱包、物品 ID、任务和成长结算。
4. worker 对活跃在线实例的扫描与旧客户端结果提交入口。

现有独占内核仍是主角状态加 `party`；新运行时暂时承载这个规则状态，以冻结行为。
这不等于已经实现 `CharacterRecord / UnitRuntime / ItemInstance` 分离。
当前输入入口可以鉴权两个成员并通过既有 PvE `combatCommand` 施法；竞技场/战场专用指令尚未接入。
不能据此声称完成两真人副本及资产生命周期。

### 3. phase 顺序需要从具体系统的行为测试提取

不能先凭直觉定义“治疗阶段”“死亡阶段”等全局编号，再让所有技能迁就它们。
当前引擎里，同一 tick 内的遍历顺序、即时死亡检查、施法结束、周期效果都有实际语义。
每个迁移点应先提供精确时间线测试，再赋予版本化 phase。

本次事件容器使用 `atMs → phase → sequence`，拒绝回插已完成阶段。
处理预算耗尽时保持当前位置，连无效事件也占预算，防止大量过期事件绕过预算。
事件仅持有有界的实体/对象引用，不持有闭包或规则对象。
容器不擅自决定施法者死亡后投射物是否保留；由对象 generation/version 的有效性判断决定。

当前投射物、普通战斗读条及战斗引导期限已迁移到堆，其余系统仍在迁移中。
把 100ms tick 包成一个事件不构成规则事件化；外层固定步进仍须逐系统替换。

### 4. 命令时点、暂停、时间域必须分别定义

服务器收到实时命令后，以 owner 的单调时钟映射确定接收时点。
实例有积压时，先用有界 slice 追到固定接收时点，再应用命令；后续命令与检查点维持顺序。
不能用每次重试重新计算的目标时间，也不能将新输入插到积压中的过去。

战斗暂停仍由已有规则冻结 `clock`、推进 `wallAt`。经济截止时间是否仍被正确执行需逐玩法验证。
本次没有重新定义多人暂停、离线两小时上限或恢复后补算策略；新 Session 恢复后从持久边界继续实时运行，
**尚未用于提供离线产品行为**。离线必须补算同一内核，不能以本次在线恢复替代。

### 5. 部署版本必须同时覆盖规则代码与内容

`game-data/manifest.json` 的内容哈希不能单独区分规则代码改动。
本次版本标识同时散列领域规则、sim-core、调度器、数据入口和实例适配器；检查点恢复拒绝不匹配版本。
最终构建流程应产出不可变 ruleset/content 标识，并规定停服恢复或版本固定策略。
不自动迁移旧存档，不清空数据库。

SQL 实验另外确认：**JSONB 的键重排会改变当前部分 AI 的配置/观察与遍历顺序**。
仅做 `JSON.stringify → JSON.parse` 的恢复测试会漏掉这个问题。
首次直接存 JSONB 的完整五人本快照，在恢复后出现 AI 决策次数与时间线偏离。
因此运行快照以 JSON 文本保存于 JSONB 元数据行内，保留嵌套对象键顺序；
用于幂等的 envelope 可以规范排序，内部规则状态不能擅自排序。
后续应将有语义的顺序显式表示为数组/序号，再评估是否改存结构化 JSONB。

### 6. 性能目标是准入策略的输入，不是已验证容量

Node Worker Threads 适合 CPU 密集的 JS；官方也建议复用线程池，避免逐任务建线程。
这支持选用固定池，但不证明 2 vCPU 可以承载多少房间。
[Node 官方文档](https://nodejs.org/api/worker_threads.html#worker-threads)

AzerothCore 的 EventProcessor 是其事件调度机制，不能据此推导整个世界只按离散事件更新。
这里只借鉴职责和调度思想，没有复制、翻译或依赖其代码。
[EventProcessor 文档](https://www.azerothcore.org/doxygen/d2/d58/classEventProcessor.html)

拒绝命令不会污染已拥有状态；随机数调用继续由同一既有规则控制。

一个规则异常会隔离本实例；不能把线程进程级崩溃也描述为只影响一个房间。

结算幂等键独立于检查点提交序号和 owner epoch。相同遭遇事实经不同检查点重试也不能再次执行资产回调；

## 非战斗活动与实体边界：后续实施决策

范围应从“战斗驻留”扩展为“活跃角色/活动驻留”，但不扩展成整个大陆常驻。
驻留、需要调度、永久提交是三个不同属性：闲置角色可以驻留且不领取 CPU；
离线角色可在持久边界卸载；交易可以低频执行且每次有明确事务。

| 业务 | 内存与调度 | 持久边界 |
| --- | --- | --- |
| 日常狩猎 | 活动运行时衔接战斗、休息、拾取和下一次开怪；复用同一战斗内核 | 击杀/任务/经验/掉落/消耗事实原子提交 |
| NPC 交互、任务 | 共享 NPC/商人/任务定义；当前角色任务视图；按命令验证，无常驻 NPC tick | 接交任务、购买、训练等命令事务；活跃角色由 owner 排序 |
| 地区旅行 | 路线和到期事件；沿途确有规则变化的节点单独调度 | 起程/改道/到达及其费用、任务变化；不模拟大陆坐标逐步行走 |
| 物品 | 活跃装备、必要背包和额度视图；静态模板共享，银行按需加载 | 永久 ID、归属、容器、数量、耐久、附魔和交易预留 |
| 普通拍卖行 | 保留系统报价/库存补货/延迟收购模型；到期事件代替高频扫描 | 上架托管、取消返还、成交到账幂等事务 |
| 金团竞拍 | 团本 owner 管理轮次与 NPC 出价；不得再有独立活动写者推进同一轮次 | 稳定竞拍/结算 ID，扣款、物品归属、分金一起提交 |
| 附魔、天赋 | 持有已确认配置，派生属性按版本失效；临时附魔按原时间规则到期 | 材料/费用/物品变更，或天赋/技能授予/洗点费用原子提交 |

目前 `inventory.js` 的普通拍卖上架使用系统收购价、30 秒期限；
`market.js` 用静态报价与角色库存状态，并不是全服玩家撮合。
不为仿照 AzerothCore 而引入新交易玩法。上述到期事件的时间域必须逐业务核对，不能在调度迁移时暗改暂停/离线规则。

实体按身份、生命周期与一致性边界拆分：

- 静态定义：CharacterClass、SpellDefinition、ItemTemplate、TalentDefinition、QuestDefinition、NpcDefinition、RegionDefinition。
- 永久记录：CharacterRecord（真人与可成长 NPC）、ItemInstance、Wallet、QuestProgress、ActivityRecord、MarketListing、RaidAuction。
- 运行对象：ResidentActivity/InstanceRuntime、UnitRuntime、Cast/Aura/Projectile、HumanController/BotController、装备与属性缓存。

普通交互 NPC 可只有静态定义及必要场景状态；可成长 NPC 有自己的 CharacterRecord、资产和控制器。
天赋分配是角色配置；永久附魔是物品状态；技能定义与一次 Cast、光环定义与一次 Aura 必须分开。
不把每个字段或每个定义都做成需要 tick 的实体，不照搬 C++ Object/WorldObject/Unit 的完整继承和客户端更新字段。

驻留的粒度由活动生命周期决定：角色在个人活动与队伍实例之间只有一个写者，进入团队时移交其运行归属，
而不是同时保留可写的个人角色副本。普通商人/训练师/任务 NPC 使用服务定义及交互校验；
可招募并成长的 NPC 具有独立角色记录、资产归属与 BotController，不能因为无人控制就作为队长的附属资产。
附魔和天赋配置变化在事务确认后按 owner 的有序边界使属性、技能与 AI 缓存失效；
静态定义共享并不代表不同角色共享可变配置。地区只在实际遭遇需要空间规则时创建运行场景。

当前 model 已分 Character/Item/Wallet，但 Character.rules、Item.data 仍是泛化对象，context() 会重新组装大 Rules。
后续应明确字段与变更事实，逐步消除“主角存档就是世界根”和拍卖物品嵌套身份。
单个角色当前归属个人活动或多人实例时，影响其战斗输入的命令必须路由到同一 owner；
资产服务执行事务，提交结果在记录过的有序边界生效，不能由经济 API 直接改角色数据库而绕过内存 owner。

AzerothCore 同时维护内存中的 Player/Item 与数据库保存接口，AuctionHouseMgr 也从数据库加载拍卖记录。
可借鉴模板/实例区分、统一单位规则与集中物品生命周期，不能把它理解为“资产只在内存，定时保存即可”。

2. `SIGKILL` 进程；新进程在旧租约未到期时必须拒绝接管。
3. 等待真实租约到期，不修改数据库时钟/租约行。

## 删除存档与永久撤销执行权（2026-10-01）

网页删除存档现在经过独立 simulation-host 的领域事务处理。服务端重新核对登录用户与存档归属，
找到存档内全部角色的实例 claim，在同一事务中增加各实例 epoch、写入永久删除标记，
删除该存档的角色、钱包、物品、活动与对应检查点/提交记录，并保存用户范围的删除回执。
保留极小的 owner 删除记录和创建/删除回执，防止重试创建、迟到的 admission 或旧 host 将实例重新建立。
业务资产删除失败时，执行权撤销和回执也一并回滚。

这是用户明确删除整个存档时的行为。删除不需要先重新结算即将被删除的个人战斗；
事务完成后，本 host 隔离并移除内存实例，等待已接受的 IO 返回，不再提交最后一次存档。
旧 owner 的检查点提交、租约续期、释放和重新获取执行权均受永久标记及 epoch 校验约束。
若 owner 运行在其他进程，即使未立即收到内存清理信号，其后续持久提交也无法重建资产。
多 host 的即时发布撤销通知仍属于后续分布式路由工作，不能把事务写入保护当作该通知已经实现。

删除回执只允许原用户查询，因此超时后重试返回同一成功结果，其他用户仍收到不存在。
网关清理被删除存档的角色元数据和路由缓存；旧网页的后续已选存档请求返回 404。
正常角色在线提交保留 `account_presence.accountId`，避免账号范围的清理遗漏在线记录。

## 补算期间的持久排队输入与结果回执（2026-10-01）

实例现在最多保留 64 条待执行指令，记录认证账号、控制器版本、客户端序号、稳定 requestId、
服务器指定的有效墙钟时点和接受序号。指令及游标进入一致检查点；接收确认需要事务提交成功。
短暂的正常在线推进仍可直接得到 applied/rejected 回执；历史补算未完成时返回 queued，
不再让 HTTP、Worker RPC 或 session IO 队列一直等待历史战斗推进到当前时刻。

Worker 每次先执行有预算的规则推进，到指令时点才应用，单轮最多应用一条指令。
同刻的其他指令保持顺序，未完成前不能越过该时点；后续指令仍经过统一权限与规则校验。
延期失败是明确的 rejected 结果，不会让整个实例隔离，也不会丢弃下一条合法输入。
再次上线跳过超出离线额度的墙钟区间时，待执行输入与墙钟锚点一起平移，保留应执行的规则时间。

检查点包含接受和应用两个输入游标。恢复校验待执行数量、输入顺序、时点、控制器、回执与游标，
拒绝缺失或损坏的排队记录。恢复从同一规则/内容版本继续执行，重试 requestId 不会重新排队或改期。
最近 256 条输入保留在边界状态，公开给当前控制角色的回执最多 80 条；过旧请求不能绕过客户端游标重新执行。

事务完成后，IO 层通知 Worker 已提交的接受/应用游标。公开回执分别表示 queued、applied、rejected
以及 durable；内存中已应用但尚未提交的结果不能被界面当作永久确认。
网页命令队列只在收到持久的成功结果后播放成功反馈和执行界面跳转，延期失败仍显示规则拒绝原因。
刷新后仍能从公开回执看到排队/待确认状态；离开页面只取消本地等待，不取消已经保存的服务器指令。

回执专项 **9/9** 通过（6.49 秒）。类型检查和 Web 构建通过，构建仍有既有的大分块提示。
真实 Worker 测试在 120 秒积压场景中接收持久 queued 回执，同时继续响应投影和检查点，
关闭并恢复后保留同一输入；确定性测试比较了包含暂停/恢复的完整状态与 RNG。

### 按实际期限唤醒常驻实例（2026-10-01）

移除 simulation worker 在每次推进完成后固定等待 25ms 的轮询。线程级最小堆按实例 ID
维护唯一条目，可以 O(log n) 取消和重排；新输入、在线状态更新和实例移除都不会留下过期条目。
实例给出下一次规则、已接受输入或离线上限的 wall deadline，再由 owner 的单调时钟映射唤醒。
预算耗尽仍立即续调，不把未完成的目标时间写成已完成。战斗内核尚未迁移的系统继续遵守
100ms 规则边界，活动结束、竞拍、捕获与旅行下马等已有独立期限也参与调度。

只对现有 `quietIdle` 判定证明无持续演化的状态停止规则轮询。个人拍卖到期和闲置 NPC 的
20 分钟成长仍有自主唤醒；NPC 的参与状态和成长间隔与实际执行共用定义。
暂停战斗和 PvP 准备阶段可以等待输入或离线上限。带宠物、光环、未完成恢复、限时任务、
副本等状态仍走保守的规则步进，不能把此改动称为所有场景已完全事件化。

休眠时检查点保留最后实际推进的时钟。授权公开/私有页面读取可以补齐已证明无战斗演化的
时间，使冷却显示继续流逝；访问校验在补齐之前，读取不补充离线额度、不推进活跃战斗，
也不越过待处理输入。普通内核投影接口默认仍只读。到达离线上限后不重复进行零时间推进。
原网页实测环境保留其旧运行版本，没有用新规则恢复旧哈希检查点。

验证：完整模拟测试 66/66 通过，106.3 秒；最终休眠与离线专项 10/10 通过；类型检查通过。
新增用例覆盖真正休眠、无请求拍卖结算、输入唤醒、NPC 成长期限、暂停后的输入恢复，
以及多次提前/延后重排后堆占用不增长。

### Worker 故障后的容量恢复（2026-10-01）

固定 Worker 池现在会替换已退出的线程。先拒绝该线程上的待处理 RPC，观察到 `exit` 后才清理
对应路由并重新使用分片槽位；其他健康线程不受影响。替换从 100ms 开始指数退避，上限 30 秒，
持续运行 60 秒后重置连续失败退避。线程分配本身失败也进入退避，避免定时器抛错导致 host 退出。
内部 inspect 增加连续重启次数、计划重启时间及失败原因；关闭 host 取消待执行的替换。

会话直接检查所属线程和 epoch 的可用性，不能在 Worker 已退出时仍被目录当作有效 owner。
重连先停止失效会话并等待已接受的 IO 结束。保留原数据库租约直到过期，不提前释放不确定提交。
随后经现有鉴权、准入和检查点恢复路径获得新 epoch；同一实例的并发恢复共享一次准入。
这是 **Worker 自动替换、实例按访问恢复**，尚未加入无人访问实例的后台恢复监督器；离线时间
仍按持久存在状态和同一内核补算。普通线程失败可能需要等待剩余的 30 秒租约，不能称为零中断。

新增真实线程故障测试覆盖已确认任务奖励、数据库已提交但尚未回执、IPC 超时、关闭时取消重启，
以及线程分配失败后的重试。两类奖励恢复均验证高 epoch、旧 owner 拒绝、原请求重试幂等、
经验/完成标记与钱包/物品/账本一致。测试仅加速 repository 的租约时钟；规则调度使用正常时钟。
这些用例使用 MemoryStore，不代替远程 PostgreSQL 多连接和进程级故障验证。

## 执行权转移的准备屏障（2026-10-01）

新增 owner 内部 quiesce/resumeExecution 操作。quiesce 在完整 Worker 消息边界取得检查点、移除该实例的
调度唤醒，并阻止其继续推进、接收输入、更新在线状态和发布投影；同 Worker 的其他房间继续运行。
它不修改玩家的战斗暂停设置，不公开为客户端暂停命令。恢复执行时沿用原时间映射，由同一规则补足允许推进的时间。

SimulationSession.prepareTransfer 先封住新请求，排完已接受的 IO/输入，再冻结 Worker、提交该边界，
最后用 transferId 和提交序号封存持久执行权。封存后普通 checkpoint、renew、release 与角色资产写入都被拒绝。
取消准备必须通过数据库 fencing 验证同一 owner/epoch/序号，之后才能唤醒 Worker；接管后的旧 owner 不得恢复。
封存回执丢失、进程关闭或十秒内未作出转移决定时，停止本地执行并保留不确定的持久边界，等待安全恢复；
不会自动解除可能已用于转移的封存。队列已满时直接拒绝准备，不会把仍有执行权的会话卡住。

本地真实 PostgreSQL 使用独立新 schema 和两个连接池，验证了另一连接无法提交封存 owner 的检查点或钱包，
以及“事务先读旧 owner、另一连接随后封存、旧事务最后提交”的竞态：旧事务回滚，序列化重试读到封存后拒绝。
替代 owner 恢复后两名角色的物品、钱包和账本不变，旧会话取消封存失败并停止其 Worker。
