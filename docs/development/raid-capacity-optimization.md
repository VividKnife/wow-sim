# 40 人团本计算性能优化

日期：2026-09-26。基于当前工作区，保留其中已有的职业、NPC、装备和团本改动。优化前调查见 [性能调查](raid-capacity-performance.md)。

## 实测结果

Apple M4、Node v24.15.0，相同初始队伍、种子和 15 秒模拟区间。下表总耗时包含规则、战斗帧、复制、团务和检查点。优化前重新预热后测一次，最终版本预热后测两次、交替场景顺序；最终测量期间没有并行运行本任务的测试。桌面环境仍可能有其他负载，所以同时保留进程 CPU 时间。

| 场景 | 人数 | 优化前总耗时 | 优化后平均总耗时 | 优化后规则 tick 平均 / P95 |
| --- | ---: | ---: | ---: | ---: |
| 卢西弗隆 | 25 | 11.08 s | 3.54 s | 14.68 / 20.65 ms |
| 卢西弗隆 | 40 | 26.52 s | 6.08 s | 27.21 / 39.18 ms |
| 管理者 | 25 | 13.19 s | 3.00 s | 11.68 / 17.77 ms |
| 管理者 | 40 | 18.63 s | 5.27 s | 22.00 / 36.21 ms |

40 人卢西弗隆的进程 CPU 时间从 24.44 s 降到平均 6.40 s，约减少 74%；管理者从 18.50 s 降到 5.48 s，约减少 70%。卢西弗隆纯规则总耗时为 4.08 s，含展示等总耗时为 6.08 s，分别占 15 秒预算的 27% 和 41%。两次墙钟样本为 6.056／6.100 s；管理者为 5.273／5.273 s。

四个场景的最终完整状态哈希均与优化前相同。40 人卢西弗隆全员存活，最大友方单位数 56；管理者存在战斗死亡，不能把它当作全员存活的压力上限。以上短区间已满足本次设定的平均计算预算，完整扩容仍须遵循文末的玩法与渲染边界。

另将 40 人卢西弗隆推进区间延长到 60 秒，预热后测一次：总墙钟 24.19 s、进程 CPU 25.45 s，全员存活，规则 tick P95 41.89 ms。战斗在约 46 秒结束，600 个采样 tick 中 462 个仍在战斗；后半段包含战后更新，因此这不是持续 60 秒满战斗负载的测试。该轮预热与测量状态哈希一致，没有做优化前的 60 秒逐步对照。

原始样本、组件耗时、状态哈希、源码哈希和验证记录见 [优化测量 JSON](../research/raid-capacity-optimization-2026-09-26.json)。

## 采用的方案

保留现有确定性战斗引擎、100 ms 逻辑步长与本地 Worker 边界。将派生属性计算和只读技能选择分开：

- `derived-cache.js` 为每个角色维护运行时依赖快照。依赖值未变时复用结果；检查嵌套字段，因此同一 tick 内的装备损坏、光环修改、天赋修改、变形、宠物死亡仍立即生效。比较实际值，不使用可能碰撞的哈希或对象引用判定。
- `character.js` 显式声明属性计算依赖，覆盖人物、宠物、护甲、抗性、种族和天赋。时间也是依赖，保证精确到期语义。HP、位置、冷却等不影响人物属性的高频字段不触发重算；恶魔猎犬的 HP 是抗性例外，单独列入。
- `talent-effects.js` 按职业和实际天赋等级编译已选天赋及技能。姿态、装备限制、临时天赋 Buff 仍按当前角色状态判断。
- `decideClass` 在展开技能属性前检查技能、分类与公共冷却。条件需要属性时才读取；一次技能选择期间复用人物属性，供条件扫描、治疗筛选与排序使用。选择结束后不保留这个只读视图，实际技能效果仍读取实时属性。
- 展示层复用技能名称的规范化结果，减少每帧为天赋触发效果反复扫描和处理字符串。

缓存使用 `WeakMap`，不进入存档、消息或回放，也不保留失去引用的角色。`stats` 和公开天赋查询继续返回可独立修改的结果，避免调用方污染缓存。

这次没有引入 ECS、WASM 或同一场战斗内的并行执行。测量表明主要问题是重复工作；先消除这些成本，可以保留现有结算顺序和随机数消费顺序。若以后把所有属性修改收敛到统一写入口，可进一步改为显式版本号失效；当前多个模块直接修改嵌套字段，直接上版本号会有漏更新风险。

## 正确性与复测方法

使用改动前保存的相同 25／40 人金团初始状态，覆盖卢西弗隆与管理者，每例推进 15 秒。`verify-raid-capacity.mjs` 每 50 ms 比较完整状态，每 100 ms 比较包含团务的战斗帧，每 10 秒比较检查点。四例共 1,200 个状态、600 个战斗帧和 4 个检查点与改动前一致。完整状态包括随机数、日志、目标、站位、伤害和治疗统计。

```sh
# 在优化前生成夹具、测量和逐步轨迹；优化后复用同一目录。
node scripts/benchmark-raid-capacity.mjs --rosters=gold --runs=2 --fixtures=.cache/raid-capacity/fixtures
node scripts/verify-raid-capacity.mjs --fixtures=.cache/raid-capacity/fixtures --trace=.cache/raid-capacity/before.json
# 应用优化后：
node scripts/verify-raid-capacity.mjs --fixtures=.cache/raid-capacity/fixtures --trace=.cache/raid-capacity/after.json --expected=.cache/raid-capacity/before.json
node scripts/benchmark-raid-capacity.mjs --rosters=gold --runs=2 --fixtures=.cache/raid-capacity/fixtures
```

本次实际复用的夹具目录为 `.cache/raid-capacity/final-fixtures`。优化前规则模块副本位于 `.cache/raid-capacity/optimization-before`，通过 Node 加载钩子对同一初始状态回放；该副本仅用于本地验证，不是生产兼容实现。

新增回归测试覆盖全部九个职业的同 tick 嵌套修改、装备损坏／修复、附魔、天赋、变形、增益到期、宠物和返回值隔离。依赖缓存检查还覆盖删除、数组变化、`Infinity` 与 `null` 的区别、不同角色之间的隔离。

验证中还修正了金团测试夹具的随机性：`GameService` 原先只固定战斗种子，角色 ID 仍用随机 UUID；而 NPC 装备与招募又以角色 ID 派生随机数，所以相同测试可能得到不同队伍和通关结果。现在同时固定 ID 生成器，包含通关用例在内的 10 个金团集成测试均通过。

验证记录：

- `npm run check`、`npm run typecheck`、`npm run data:check` 通过，内容清单已重新生成。
- 新增 4 个属性缓存测试全部通过；其中一个覆盖九个职业的一系列嵌套修改。单人、副本、团本、竞技场、战场的 Worker 原地推进与不可变推进逐步一致性测试均通过。
- 全量测试初跑 1,657 项：1,639 通过、12 失败、6 跳过。固定金团夹具后，单独复跑该文件的全部 10 项均通过；固定后的通关用例在优化前代码上也通过。
- 其余 11 个失败均使用优化前规则副本复现：协议与增量事件的负零序列化（2）、地图飞行位置（2）、暴风雪伤害次数（1）、奥妮克希亚通关（1）、熔火之心五个首领的通关或时限断言（5）。奥妮克希亚及五个熔火之心失败的断言详情前后完全相同。这些既有行为问题没有在性能改造中调整。
- 聚焦职业／策略的 91 项复测为 90 通过、1 个上述既有暴风雪失败。完整日志保存在 `.cache/raid-capacity/`。

## 维护边界

- `calculateStats` 及其调用函数新增角色字段依赖时，必须同步更新 `cachedStats` 的依赖清单和失效测试。静态内容表在一个内容版本内不可热修改。
- 技能选择阶段必须保持只读；产生战斗副作用后不得继续使用同一个决策属性视图。当前唯一可能在变形后继续筛选的弹药失败分支会清空该视图。
- 这次解决计算热路径，不等于正式开放 40 人金团。招募席位、指挥视图和首领数值仍按当前 25 人玩法运行；40 人只在内存压力夹具中绕过容量限制。
- 基准包含规则、投影、复制和检查点，不包含浏览器主线程、React、GPU、数据库或网络。不能据此宣称 40 人画面已达到指定 FPS。高频帧的数据体积和完整总览投影仍是后续优化点。
