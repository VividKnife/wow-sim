# 战斗运行与回放

实现日期：2026-09-18。

## 共用规则，两种运行模式

`rules/engine.js` 的 `advance` 是唯一的伤害、AI、移动、技能、随机数及掉落计算入口。记录器通过只读观察回调采样这条时间线，不实现第二套战斗规则。普通单人默认无需中途操作。

| 场景 | 模式 | 执行方式 |
| --- | --- | --- |
| 个人狩猎 | recorded | worker 预计算当前遭遇，客户端播放 |
| 一个账号的副本，包括 NPC 队友和佣兵 | recorded | 与个人狩猎共用记录器 |
| 多个账号参加的副本 | realtime | 保留现有服务器实时推进和指令处理 |
| 内容声明 `combat.requiresManualControl` 的遭遇 | realtime | 必须由服务器内容在开战时设置，普通客户端指令无法设置 |
| 单人离线挂机或积压补算 | 批量推进 | 共用规则，不生成未来动画记录 |

不要按队伍角色数量判断多人：一个玩家带四名伙伴依然是单人。

## 预计算、时间与持久化

1. worker 读取已提交的活动/实例状态及其 `simulationVersion`。
2. 关闭读取事务，在内存里模拟至本场结束；单段最多 60 秒、600 ticks。超长战斗在下一段继续。
3. 短事务检查活动仍在运行、版本未变化、没有其他 worker 已发布记录，然后保存 `combat_plans` 并发布轻量的 `playback` 元数据。
4. 权威角色存档留在当前检查点。`nextEventAt` 指向预计算段的真实结束时间，期间 worker 不再每 200 ms 重写该战斗。
5. 到真实时间边界后，事务消费未来检查点，持久化角色、物品和收益，记录幂等结算事件。继续自动狩猎/副本推进时再生成下一段。

每个活动或实例最多保留一条计划；消费、指令失效或账号重建时清理。计划包含完整恢复状态，worker 重启不需要重新掷随机数。不存在浏览器上传结果、播放完成后客户端决定奖励，或通过修改客户端时钟提前结算的路径。

一场战斗若跨越多个段，已经发生的收益可以在段边界提交；不会提交尚未经过的游戏时间。角色占用、法力、复活及其他活动期限仍按服务器时间判断。

## 回放协议与前端

游戏快照新增 `combatMode` 与 `playback` 元数据。动画数据由鉴权的 `GET /game/replay?id=...&characterId=...` 单独读取，Web 代理入口为 `/api/game/replay`。

记录由公开初始战斗投影、100 ms 状态差量和新增日志事件组成。日志只追加新事件并按首条 ID 截断，不反复传输整个日志数组。投影不包含未来背包、金币、随机种子或服务器最终存档。

前端根据接口返回的 `serverNow` 建立本地单调时钟，复用现有 Battle、Pixi、插值、音效和伤害统计。刷新和重新打开窗口会恢复至服务器对应进度。数据未到齐或段已播放完时，画面不会越过已知段的末尾推演伤害。

有计划时普通快照轮询降到 2 秒，用于在线心跳、发现指令变更和下一段；不再逐帧请求状态。动画更新只重渲染 Battle，不让世界、商店和策略页面跟着每个动画帧重渲染。客户端最多缓存四个回放段。没有计划的实时战斗继续使用原有 200 ms 观察轮询。

## 指令与重新计算

当前保留停止、暂停自动推进、策略修改、放弃战斗等已有操作。收到指令时，从已提交状态推进到服务器当前时刻，应用操作，提升模拟版本并删除未生效的计划；worker 随后生成新的后续记录。失败的指令通过事务回滚保留原计划。

这也为后续干预战斗提供了基础。当前没有任意拖动时间线或回到过去重新结算的接口。若增加明确的手动玩法，应在开战前向玩家展示该模式；如果未来允许暂停回放后从该位置干预，还需定义独立的可操作时间边界，不能直接相信客户端传入的时间戳。

## 挂机与负载

单人离线战斗使用 30 秒调度间隔，每次最多推进 3,000 ticks（通常对应 5 分钟模拟时间）。玩家回来时，如果单人状态积压超过 2 秒，同样按批次补算，避免退回每事务只处理 20 ticks。非战斗旅行和后台生产保持原有规则；固定活动完成时间、复活结束时间和离线上限会优先唤醒任务。

默认两小时离线上限仍有效，重连不会将超出的离线时间补记为收益。无人在线时不创建未来回放；在线自动战斗即使暂时关闭窗口也会准备当前段，但浏览器只在打开战斗窗口时下载。

物品和钱包持久化跳过未变化的数据，避免在战斗检查点重复写入全部装备和背包。
